An ORM maps Java objects to database rows so you work with entities instead of hand-written SQL. JPA is the standard that defines this mapping, Hibernate implements it, and Spring Data JPA removes the repository boilerplate on top.

---

## The Persistence Stack

```
Application
    ↓
Spring Data JPA        (repository abstraction)
    ↓
JPA                    (specification: interfaces & annotations)
    ↓
Hibernate              (JPA provider: implementation)
    ↓
JDBC                   (low-level SQL driver)
    ↓
Database
```

- **JDBC**: lowest-level API; executes raw SQL and manages connections, statements, and result sets. Hibernate uses JDBC under the hood.
- **JPA (Java Persistence API)**: a specification. It defines annotations (`@Entity`, `@Id`), interfaces (`EntityManager`), JPQL, transaction rules, and relationship mapping, but ships no implementation. Providers: Hibernate (most common), EclipseLink, Apache OpenJPA.
- **Hibernate**: the most popular JPA provider. A full ORM that converts entities to SQL, maps result sets back to objects, and supports caching (L1/L2), lazy/eager loading, and query optimization.
- **Spring Data JPA**: sits on top of JPA and generates repository implementations at runtime, eliminating DAO boilerplate. See [3.2 Spring Data JPA](<3.2. Spring Data JPA.md>).

When you call `userRepository.save(user)`, Spring Data JPA delegates to `entityManager.persist(user)`; Hibernate turns that into an SQL `INSERT`, which JDBC sends to the database.

## Entity Annotations

### `@Entity` and `@Table`

`@Entity` marks a class as a JPA entity. `@Table` customizes the table mapping (optional; defaults to the class name).

```java
@Entity
@Table(name = "employees")
public class Employee {
    // ...
}
```

`@Table` attributes: `name`, `schema`, `catalog`, `uniqueConstraints`, `indexes`.

> **Note**: in production with Flyway/Liquibase and `ddl-auto=validate`, typically only `name` is set; schema, unique constraints, and indexes live in migration scripts (the other `@Table` attributes mainly drive Hibernate's DDL generation). Configure schema globally via `spring.jpa.properties.hibernate.default_schema` or the JDBC URL, and set `schema` per-entity only for multi-schema apps.

### `@Id` and `@GeneratedValue`

`@Id` marks the primary key; `@GeneratedValue` delegates ID generation to the provider.

```java
@Entity
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "emp_seq")
    @SequenceGenerator(name = "emp_seq", sequenceName = "employee_seq", allocationSize = 50)
    private Long id;
}
```

| Strategy   | Behavior                                                  | Notes                                                  |
|------------|-----------------------------------------------------------|--------------------------------------------------------|
| `SEQUENCE` | Uses a DB sequence; fetches the ID before the INSERT      | Preferred for PostgreSQL; enables JDBC batching        |
| `IDENTITY` | DB auto-increment; runs the INSERT immediately to get the ID | Simple, but breaks batching                         |
| `UUID`     | Standard UUID generation (JPA 3.1+)                       | Globally unique, hides ID scale, good for distributed systems |
| `AUTO`     | Hibernate picks based on the dialect                     | Avoid; be explicit                                     |
| `TABLE`    | A separate table simulating sequences                    | Legacy only, avoid                                     |

> **Note**: `IDENTITY` forces Hibernate to execute each `INSERT` immediately to read the generated key, giving N round-trips for N inserts and disabling JDBC batching. `SEQUENCE` pre-fetches IDs in blocks (`allocationSize`), so Hibernate batches inserts into one round-trip, the preferred choice for high-throughput PostgreSQL.

### `Long` vs `UUID`

Most apps use a surrogate `@GeneratedValue Long id`, but UUIDs are common for public-facing IDs.

| Feature             | Long (sequential)                            | UUID                                          |
|---------------------|----------------------------------------------|-----------------------------------------------|
| Performance         | Faster indexing/joins (8 bytes, sequential)  | Slightly slower (16 bytes, non-sequential)    |
| Security            | Guessable (scrapeable via `id+1`)            | Hard to guess (hides system size)             |
| Distributed systems | Hard to coordinate across nodes              | Easy; generated in-app without DB sync        |
| Storage             | 64-bit (`BIGINT`)                            | 128-bit (`UUID` / `BINARY(16)`)               |

- Use `Long` for internal entities, high-throughput join tables, or when ID obfuscation does not matter.
- Use `UUID` for public-facing entities (URLs, APIs) and distributed systems, to prevent ID-enumeration attacks and allow in-app generation.

```java
@Id
@GeneratedValue(strategy = GenerationType.UUID) // JPA 3.1+ / Spring Boot 3.0+
private UUID id;
```

```java
@Id
@GeneratedValue
@UuidGenerator(style = UuidGenerator.Style.TIME) // time-based, more index-friendly than random
private UUID id;
```

### Surrogate PK + Composite Unique

The modern default for nearly all entities is a surrogate primary key (`@GeneratedValue Long id`, auto-generated, no business meaning) plus a composite UNIQUE constraint when you need multi-column uniqueness. A surrogate PK is stable (unaffected by business-field renames), compact (a single `BIGINT` indexes and joins faster than a composite), and simple to map.

```java
@Entity
@Table(
    name = "reviews",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_review_per_user_product",
        columnNames = { "user_id", "product_id" }
    )
)
public class Review {

    @Id @GeneratedValue
    private Long id; // surrogate PK

    @ManyToOne
    @JoinColumn(name = "user_id")
    private User user;

    @ManyToOne
    @JoinColumn(name = "product_id")
    private Product product;

    private Integer rating;
    private String comment;
}
```

This enforces "one review per user per product" at the DB level while keeping a clean surrogate PK. Reach for a composite primary key only for a true compound natural key with business meaning, a pure join table with no extra columns, or legacy DB interop.

### Composite Primary Keys (`@EmbeddedId` vs `@IdClass`)

When the key itself spans multiple columns, use a composite PK via one of two approaches.

**`@EmbeddedId` (preferred)**: wrap the key fields in an `@Embeddable` class and reference it as a single ID field.

```java
@Embeddable
public class ReviewId implements Serializable {
    private Long userId;
    private Long productId;
    // equals, hashCode, no-args + all-args constructors
}

@Entity
public class Review {
    @EmbeddedId
    private ReviewId id;
    private Integer rating;
    private String comment;
}
```

**`@IdClass` (legacy)**: define a parallel ID class with the same field names and mark each PK field on the entity with `@Id`.

```java
public class ReviewId implements Serializable {
    private Long userId;
    private Long productId;
    // equals, hashCode
}

@Entity
@IdClass(ReviewId.class)
public class Review {
    @Id private Long userId;
    @Id private Long productId;
    private Integer rating;
    private String comment;
}
```

| Aspect            | `@EmbeddedId`                 | `@IdClass`                                  |
|-------------------|-------------------------------|---------------------------------------------|
| ID accessed via   | `review.getId().getUserId()`  | `review.getUserId()`                        |
| Boilerplate       | Less (single key class)       | More (duplicate fields on entity + ID class) |
| Modern preference | Yes                           | Legacy / older-code interop                 |

Both approaches require the ID class to:

- Implement `Serializable`.
- Override `equals()` and `hashCode()` on all key fields.
- Provide a no-args constructor.

### `@MapsId`

When a composite-key entity also has `@ManyToOne` relationships pointing to the same columns that form the PK (typical for join entities with extra fields), use `@MapsId` so the FK column doubles as part of the embedded PK. Without it, Hibernate fails with "Repeated column in mapping for entity" because the column is declared twice (once in the ID, once via `@JoinColumn`).

```java
@Entity
public class Review {

    @EmbeddedId
    private ReviewId id;

    @ManyToOne(fetch = FetchType.LAZY)
    @MapsId("userId")                    // shares id.userId
    @JoinColumn(name = "user_id")
    private User user;

    @ManyToOne(fetch = FetchType.LAZY)
    @MapsId("productId")                 // shares id.productId
    @JoinColumn(name = "product_id")
    private Product product;

    private Integer rating;
    private String comment;
}
```

`@MapsId("userId")`:

- Tells Hibernate the FK column for this relationship is the `userId` field of the embedded ID.
- Avoids mapping the same column twice.
- Populates `id.userId` automatically when you call `review.setUser(user)`.

With a surrogate `id` + composite UNIQUE (the default above), `@MapsId` is not needed, since the relationships are independent of the PK.

### `@Column`

Customizes the column mapping.

```java
@Column(name = "full_name", nullable = false, length = 50, updatable = false)
private String name;
```

Common options: `name`, `nullable`, `unique`, `length`, `updatable`, `insertable`.

### `@CreationTimestamp` and `@UpdateTimestamp`

Hibernate-specific (not pure JPA); populated automatically on insert and update.

```java
@CreationTimestamp
private LocalDateTime createdAt;

@UpdateTimestamp
private LocalDateTime updatedAt;
```

## Hibernate Configuration

| Property                                      | Description                  |
|-----------------------------------------------|------------------------------|
| `spring.jpa.hibernate.ddl-auto`               | Controls schema generation   |
| `spring.jpa.show-sql`                         | Prints SQL to the console    |
| `spring.jpa.properties.hibernate.format_sql`  | Pretty-prints the SQL        |
| `spring.jpa.properties.hibernate.dialect`     | SQL dialect for the target DB |

### ddl-auto values

| Value         | Meaning                                       |
|---------------|-----------------------------------------------|
| `none`        | No action (default for non-embedded DBs)      |
| `validate`    | Validates the schema against entities at startup |
| `update`      | Updates the schema if entities changed        |
| `create`      | Drops and recreates the schema                |
| `create-drop` | Same as `create`, plus drops at shutdown      |

In production use `validate` or `none`, and use Flyway/Liquibase for real schema changes, since `update` can silently corrupt schemas on a rename or type change.

### SQL Init Properties

| Property                           | Default                | Values                     |
|------------------------------------|------------------------|----------------------------|
| `spring.sql.init.mode`             | `embedded`             | `always`, `embedded`, `never` |
| `spring.sql.init.schema-locations` | `classpath:schema.sql` | Any path                   |
| `spring.sql.init.data-locations`   | `classpath:data.sql`   | Any path                   |

When Hibernate creates the schema and `data.sql` seeds it, ordering matters:

```yaml
spring:
  jpa:
    defer-datasource-initialization: true
```

With this, Hibernate creates the tables before `data.sql` runs; without it, `data.sql` may execute before the tables exist and fail.

## Other JPA Topics

- **JPQL (Java Persistence Query Language)**: an object-oriented query language that uses entity names, not table names; Hibernate translates JPQL to SQL via the dialect.
- **Entity management**: Java classes mapped to tables, managed via `EntityManager`. See [3.5 EntityManager, Persistence Context & Entity Lifecycle](<3.5. EntityManager, Persistence Context & Entity Lifecycle.md>).

## Q&A

1. **JPA vs Hibernate vs Spring Data JPA?**
JPA is a specification (interfaces and annotations, no code). Hibernate is the most common JPA provider; it implements the spec and generates SQL. Spring Data JPA sits on top of JPA and generates repository implementations at runtime to eliminate DAO boilerplate.

2. **What is JPQL and how does it differ from SQL?**
JPQL queries entity classes and fields, not tables and columns. Hibernate translates JPQL to SQL using the configured dialect, which keeps it portable across databases.

3. **What `ddl-auto` value should you use in production?**
`validate` or `none`. `update` looks convenient but can silently corrupt schemas on a rename or type change. Use Flyway or Liquibase for real migrations.

4. **`@EmbeddedId` vs `@IdClass`, which and why?**
Both define composite primary keys. `@EmbeddedId` wraps the key fields in one `@Embeddable` class (modern preference, less boilerplate, a single cohesive ID field); `@IdClass` keeps the PK fields on the entity but needs a parallel ID class with the same fields. Use `@EmbeddedId` for new code, `@IdClass` for legacy interop. Both require the ID class to implement `Serializable`, override `equals`/`hashCode`, and provide a no-args constructor.

5. **Long vs UUID for primary keys?**
`Long` wins on performance (8 bytes, sequential, faster indexing and joins); `UUID` wins on distribution (generated in-app, no DB coordination) and security (not guessable, prevents ID enumeration). Use `Long` for internal/high-throughput tables and `UUID` for public-facing entities or distributed architectures.
