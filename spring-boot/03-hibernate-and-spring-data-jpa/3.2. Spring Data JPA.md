Spring Data JPA provides a repository abstraction over JPA (with Hibernate as the default implementation underneath), giving automatic query generation from method names, built-in pagination and sorting, and no manual DAO code.

Instead of writing `entityManager.persist(...)` or `entityManager.createQuery(...)`, you declare an interface:

```java
public interface UserRepository extends JpaRepository<User, Long> { }
```

Full CRUD (`save`, `findById`, `findAll`, `delete`, `count`) is inherited automatically; Spring generates the implementation at runtime via a proxy, and custom query methods are added on top.

---

## Repository Hierarchy

```
Repository                                  (marker, no methods)
   ├── CrudRepository → ListCrudRepository  (save, findById, delete, count)
   └── PagingAndSortingRepository → ListPagingAndSortingRepository  (Sort, Pageable)

JpaRepository  extends ListCrudRepository + ListPagingAndSortingRepository
               (+ QueryByExampleExecutor): adds batch ops, flush(), JPA-specific methods
```

Most applications extend `JpaRepository<EntityType, IdType>` for the full feature set.

> **Note**: since Spring Data 3.0 (Spring Boot 3.0), `PagingAndSortingRepository` no longer extends `CrudRepository`; they are siblings and `JpaRepository` composes both. Earlier versions used a single linear chain.

**Built-in methods** (inherited):

- **Read**: `findAll()`, `findById(id)`, `findAll(Pageable)`, `findAll(Sort)`.
- **Existence / count**: `count()`, `existsById(id)`.
- **Save**: `save(entity)`, `saveAll(entities)`, `saveAndFlush(entity)`, `saveAllAndFlush(entities)`.
- **Delete**: `deleteById(id)`, `delete(entity)`, `deleteAll()`, `deleteAllInBatch()`.

## CRUD Operations

```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;

    // Create
    public User createUser(String email) {
        User user = new User(email);                 // id is null
        return userRepository.save(user);            // INSERT
    }

    // Read by id
    public User getUser(Long id) {
        return userRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("User", id));
    }

    // Read all
    public List<User> getAllUsers() {
        return userRepository.findAll();
    }

    // Update
    public User updateEmail(Long id, String newEmail) {
        User user = userRepository.findById(id).orElseThrow();
        user.setEmail(newEmail);
        return userRepository.save(user);            // UPDATE
    }

    // Delete
    public void deleteUser(Long id) {
        userRepository.deleteById(id);               // DELETE
    }
}
```

`save()` on an entity with no ID issues an `INSERT`; on one with an existing ID it issues an `UPDATE`. `findById` returns an `Optional`.

## Derived Query Methods

Spring parses repository method names and builds queries automatically. A derived method reads as a return type, a query subject, `By`, and a predicate:

```
ReturnType   QuerySubject   By   QueryPredicate(InputParams)
```

```java
public interface UserRepository extends JpaRepository<User, Long> {
    List<User> findByEmail(String email);
    List<User> findByNameAndStatus(String name, String status);
}
```

Spring converts `findByEmail` to JPQL `SELECT u FROM User u WHERE u.email = :email`, which Hibernate translates to SQL. Method names start with a subject prefix (`findBy`, `readBy`, `getBy`, `queryBy`, `countBy`, `existsBy`, `deleteBy`, `removeBy`) followed by predicates.

### Operators and Keywords

Derived methods support limiting, distinct, boolean combinations, and many comparison operators (`Between`, `LessThan`, `GreaterThanEqual`, `Like`, `StartingWith`, `In`, `IsNull`).

```java
Employee findFirstByName(String name);
List<Employee> findTop5ByStatus(String status);
List<Employee> findFirst3ByOrderByCreatedAtDesc();
List<Employee> findDistinctByName(String name);

List<Employee> findByNameAndStatus(String name, String status);
List<Employee> findByEmailOrPhone(String email, String phone);

List<Employee> findByCreatedAtBetween(LocalDateTime start, LocalDateTime end);
List<Employee> findBySalaryGreaterThanEqual(Double salary);
List<Employee> findByNameLike(String pattern);          // caller passes wildcards: "%john%"
List<Employee> findByEmailStartingWith(String prefix);
List<Employee> findByStatusIn(List<String> statuses);
List<Employee> findByManagerIsNull();                   // employees with no manager
```

Full list: [official keywords reference](https://docs.spring.io/spring-data/jpa/reference/repositories/query-keywords-reference.html).

> **Note**: derived methods bind parameters positionally to the predicates in the name. `findByNameAndStatus(String name, String status)` binds the first argument to `Name`, the second to `Status`; swapping them silently runs the wrong query with no compile error. Parameter names do not matter, only order. For named binding, use `@Query` with `@Param`.

### Nested Property Queries

If the entity has a relationship, traverse it by property name and Spring generates the JOIN automatically.

```java
@Entity
public class Order {
    @ManyToOne
    private User user;
}

public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByUserName(String name);   // JOIN on order.user.name
}
```

## @Query (JPQL and Native)

Use `@Query` when a derived method cannot express the query: long names, JOINs, subqueries, aggregations, or native SQL. The same query in three styles:

```java
public interface UserRepository extends JpaRepository<User, Long> {

    // 1. Derived, getting unwieldy
    List<User> findByNameAndStatusAndTypeAndCreatedAtBetween(
        String name, String status, String type, LocalDateTime start, LocalDateTime end
    );

    // 2. JPQL @Query: entity-aware, portable across databases
    @Query("""
        SELECT u FROM User u
        WHERE u.name = :name
          AND u.status = :status
          AND u.type = :type
          AND u.createdAt BETWEEN :start AND :end
        """)
    List<User> findFilteredUsers(
        @Param("name") String name,
        @Param("status") String status,
        @Param("type") String type,
        @Param("start") LocalDateTime start,
        @Param("end") LocalDateTime end
    );

    // 3. Native SQL: when JPQL cannot express what you need
    @Query(value = """
        SELECT * FROM users
        WHERE name = :name AND status = :status
          AND type = :type AND created_at BETWEEN :start AND :end
        """, nativeQuery = true)
    List<User> findFilteredUsersNative(
        @Param("name") String name,
        @Param("status") String status,
        @Param("type") String type,
        @Param("start") LocalDateTime start,
        @Param("end") LocalDateTime end
    );
}
```

| Concern                                                  | JPQL `@Query`            | Native SQL                                 |
|----------------------------------------------------------|--------------------------|--------------------------------------------|
| Simple filtering on entity fields                        | Works                    | Works, slightly shorter                    |
| JOINs across entity associations (`JOIN u.orders`)       | Yes (entity-aware)       | No (manual `JOIN orders ON ...`)           |
| `JOIN FETCH` to avoid N+1                                 | Yes (built-in)           | No (does not exist)                        |
| `SELECT new DTO(...)` projection                         | Yes (direct)             | No (manual mapping)                        |
| DB-specific features (window functions, CTEs, JSON, UPSERT) | No (limited)          | Yes (required)                             |
| Refactor safety (renaming a field)                       | Yes (caught at startup)  | No (silent breakage; column names in a string) |
| DB portability (MySQL to PostgreSQL)                     | Yes (mostly portable)    | No (tied to the dialect)                   |

> **Note**: prefer JPQL `@Query` by default (entity-aware, refactor-safe, DB-portable). Reach for native SQL only when you genuinely need DB-specific features (window functions, CTEs, JSON operators, vendor hints, complex UPSERT). For highly dynamic queries with many optional filters, use the Criteria API or QueryDSL / `Specification`.

## Bulk Updates and Deletes

For high-volume operations where entity-by-entity `save()` would be too slow (thousands of rows in N round-trips), use a `@Modifying` `@Query` to run a single SQL statement.

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Modifying
    @Query("UPDATE Product p SET p.price = p.price * 1.1 WHERE p.category = :cat")
    int bulkRaisePrice(@Param("cat") String category);

    @Modifying
    @Query("DELETE FROM Token t WHERE t.expiresAt < CURRENT_TIMESTAMP")
    int deleteExpiredTokens();
}
```

- `@Modifying` is required for any UPDATE/DELETE through `@Query`; without it, Spring runs the JPQL as a `SELECT` and fails.
- The return type is `int`, the number of rows affected.
- It must be called inside a `@Transactional` method.

> **Note**: bulk queries go straight to the database, so entities already loaded in the same transaction keep their old values (stale data).

```java
Product p = productRepository.findById(1L).orElseThrow();    // p.price = 100
productRepository.bulkRaisePrice("electronics");             // DB: price -> 110
log.info(p.getPrice());                                      // prints 100, stale
```

Two flags fix this:

- `clearAutomatically = true` clears the persistence context after the bulk query, so the next `findById` fetches fresh from the DB.
- `flushAutomatically = true` pushes pending unsaved changes to the DB before the bulk query runs, so it sees them.

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("UPDATE Product p SET p.price = p.price * 1.1 WHERE p.category = :cat")
int bulkRaisePrice(@Param("cat") String category);
```

> **Note**: bulk queries also skip lifecycle callbacks (`@PrePersist`/`@PreUpdate`), auditing fields, and `@SQLDelete` soft-delete. Prefer `save()` / `delete()` for normal writes.

## Calling Stored Procedures

For databases that wrap business logic in stored procedures, Spring Data offers `@Procedure`.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Procedure(name = "calculate_discount")
    BigDecimal calculateDiscount(@Param("orderId") Long orderId);
}
```

The procedure must be declared on the entity via `@NamedStoredProcedureQuery`:

```java
@Entity
@NamedStoredProcedureQuery(
    name = "calculate_discount",
    procedureName = "sp_calculate_discount",
    parameters = {
        @StoredProcedureParameter(mode = ParameterMode.IN,  name = "orderId",  type = Long.class),
        @StoredProcedureParameter(mode = ParameterMode.OUT, name = "discount", type = BigDecimal.class)
    }
)
public class Order { ... }
```

Use it for:

- Legacy databases with business logic already in stored procedures.
- Multi-step or bulk computations that run close to the data to cut network round-trips (scan millions of rows, return one aggregate).
- Compliance or audit requirements that mandate database-side logic.

Avoid it for:

- New apps where logic can live in the service layer (more testable, version-controlled).
- Cross-database portability, since procedures are dialect-specific.
- Most CRUD, where `@Query` or derived methods are simpler.

## How It Works Internally

On startup, Spring scans repository interfaces, creates a proxy implementation per interface, parses method names into query semantics, and executes them via `EntityManager`; Hibernate translates the JPQL to SQL over JDBC. You never implement the DAO yourself, Spring Data JPA just hides the JPA, `EntityManager`, Hibernate, and JDBC underneath.

## Q&A

1. **What does Spring Data JPA add on top of JPA?**
Repository abstraction, query derivation from method names, pagination/sorting helpers, and runtime proxy implementations, all of which remove the manual DAO layer. Under the hood it still uses JPA, `EntityManager`, and Hibernate.

2. **How does Spring generate a query from a method name like `findByEmailAndStatus`?**
At startup it scans repository interfaces, parses each name into a subject (`findBy`) and predicate (`EmailAndStatus`), and builds a JPQL query. Method parameters bind to predicates in order.

3. **`JpaRepository` vs `CrudRepository` vs `PagingAndSortingRepository`?**
`CrudRepository` gives basic CRUD; `PagingAndSortingRepository` adds `findAll(Pageable)` / `findAll(Sort)`. Since Spring Data 3.0 the two are siblings, and `JpaRepository` composes both and adds batch operations and `flush()`. Extend `JpaRepository` unless you have a reason not to.

4. **When would you use `@Query` over a derived method?**
When the method name would become unreadable, when you need JPQL constructs derivation cannot express (`JOIN FETCH`, subqueries, `SELECT new ...` DTO), or when you need a native query.

5. **What is the difference between JPQL and native queries?**
JPQL queries entity classes and fields and is DB-portable; native queries use raw SQL, needed for DB-specific features (window functions, CTEs) but tied to that vendor's dialect.

6. **Why does an UPDATE/DELETE `@Query` need `@Modifying`, and what about `clearAutomatically` / `flushAutomatically`?**
Without `@Modifying`, Spring runs the JPQL as a `SELECT` and fails. Bulk modifying queries bypass the persistence context, so loaded entities keep stale state; `clearAutomatically = true` evicts them and `flushAutomatically = true` pushes pending changes first. Use them when the same transaction reads or saves affected entities afterward.

7. **When would you use `@Procedure` over `@Query`?**
For databases with existing business logic in stored procedures, or when performance-critical computations benefit from running in-database. The procedure must be declared via `@NamedStoredProcedureQuery`. For new apps, prefer service-layer logic with `@Query` (more testable, version-controlled, DB-portable).

## Quick Revision Cheat Sheet

| Concept                                  | Remember                                                       |
|------------------------------------------|----------------------------------------------------------------|
| `JpaRepository<T, ID>`                   | Extend for full CRUD + paging + batch; proxied at runtime      |
| Derived query                            | Parsed from the method name; params bind positionally          |
| `@Query` (JPQL)                          | Default for complex queries; entity-aware, refactor-safe       |
| Native query                             | `nativeQuery = true`; only for DB-specific features            |
| `@Modifying`                             | Required for `@Query` UPDATE/DELETE; needs `@Transactional`    |
| `clearAutomatically` / `flushAutomatically` | Evict stale entities after / flush pending before a bulk query |
| `@Procedure`                             | Calls a stored proc declared via `@NamedStoredProcedureQuery`  |
| Paging vs Crud (3.0+)                    | `PagingAndSortingRepository` no longer extends `CrudRepository` |
