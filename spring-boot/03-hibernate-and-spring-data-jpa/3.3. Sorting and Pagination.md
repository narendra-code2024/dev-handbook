Spring Data handles sorting and pagination through `Sort`, `Pageable`/`Page`, and, for deep paging, keyset scrolling, so you rarely write the SQL yourself.

---

## Sorting

### Via Method Name (`OrderBy`)

```java
public interface EmployeeRepository extends JpaRepository<Employee, Long> {
    List<Employee> findAllByOrderByNameAsc();
    List<Employee> findByDepartmentOrderByNameDesc(String department);
}
```

Rules:

- `OrderBy` comes after the `By` clause and any query conditions.
- Direction (`Asc`/`Desc`) is optional; the default is `ASC`.
- **Limitation**: the field and direction are hardcoded, so you cannot change them at runtime.

### Via Sort Parameter (dynamic)

Accept a `Sort` object at the call site, which is fully dynamic and supports multiple fields.

```java
public interface EmployeeRepository extends JpaRepository<Employee, Long> {
    List<Employee> findByDepartment(String department, Sort sort);
}

// caller
Sort sort = Sort.by(Sort.Direction.ASC, "name");
List<Employee> employees = employeeRepository.findByDepartment("IT", sort);

// multiple fields
Sort multi = Sort.by(
    Sort.Order.asc("name"),
    Sort.Order.desc("salary")
);
```

`JpaRepository` already exposes `findAll(Sort)`, so no extra declaration is needed to sort the full table.

```java
List<Employee> employees = employeeRepository.findAll(Sort.by("name").descending());
```

## Pagination

Pagination splits large result sets into smaller pages. Core types:

- **`Pageable`**: input interface carrying page number, size, and optional sort.
- **`PageRequest`**: concrete `Pageable` you construct via `PageRequest.of(...)`.
- **`Page<T>`**: the returned result; carries the items on this page plus pagination metadata:
    - `getContent()`: items on the current page.
    - `getTotalElements()`: total row count.
    - `getTotalPages()`: total page count.
    - `getNumber()`: current page index (zero-based).
    - `isFirst()` / `isLast()`: boundary checks.

### Using Page, Pageable, PageRequest

```java
public interface UserRepository extends JpaRepository<User, Long> {
    Page<User> findByLastName(String lastName, Pageable pageable);
}

// caller: page 0 (first page), 10 records
Pageable pageable = PageRequest.of(0, 10);
Page<User> page = userRepository.findByLastName("Smith", pageable);

// combining pagination + sorting
Pageable sortedPage = PageRequest.of(0, 5, Sort.by("salary").descending());
```

Spring Data JPA fires two queries for a `Page<T>` result; the count query mirrors the main query's `WHERE` clause:

```sql
-- main query
SELECT * FROM employee WHERE last_name = ? LIMIT ? OFFSET ?;

-- count query
SELECT COUNT(*) FROM employee WHERE last_name = ?;
```

> **Note**: deep pagination is expensive. `OFFSET 100000` makes the database scan and discard 100k rows before returning the next page, and cost grows linearly with depth. `Page<T>` + `OFFSET` is fine for admin UIs and shallow pages; for infinite scroll or millions of rows, prefer cursor (keyset) pagination.

### Cursor (Keyset) Pagination

Pages are anchored by the last seen sort value instead of an offset, giving constant query cost no matter how deep you go.

```sql
SELECT * FROM employee
WHERE id > :lastSeenId
ORDER BY id
LIMIT 20;
```

Each page returns the items plus the last `id` seen; the client passes that back as `lastSeenId` for the next page. With no `OFFSET`, the DB seeks directly to the cursor via the index. Spring Data offers two styles:

```java
public interface EmployeeRepository extends JpaRepository<Employee, Long> {

    // Naive cursor: derived method, caller passes lastSeenId
    List<Employee> findByIdGreaterThanOrderByIdAsc(Long lastSeenId, Pageable limit);

    // Spring Data 3.1+: built-in keyset support via Window<T>
    Window<Employee> findByOrderByIdAsc(ScrollPosition position, Limit limit);
}
```

```java
@GetMapping("/employees")
public CursorPageResponse<EmployeeDto> list(
    @RequestParam(required = false) String cursor,
    @RequestParam(defaultValue = "20") int limit
) {
    // missing cursor → first page; present → decoded keyset position
    ScrollPosition position = (cursor == null || cursor.isBlank())
        ? ScrollPosition.keyset()
        : cursorCodec.decode(cursor);

    Window<Employee> window = employeeRepository.findByOrderByIdAsc(position, Limit.of(limit));

    // include nextCursor only if more pages exist
    String nextCursor = window.hasNext()
        ? cursorCodec.encode(window.positionAt(window.size() - 1))
        : null;

    return new CursorPageResponse<>(toDto(window.getContent()), nextCursor);
}
```

> **Note**: `cursorCodec` is a custom helper you write, typically Base64-encoded JSON of the cursor's keys. Spring ships none because the encoding choice (Base64-JSON, JWT-signed, etc.) is yours.

Requirements and trade-offs:

- **Sort is mandatory**: the cursor encodes where you left off in the sort column, so no sort means no cursor.
- **The cursor encodes the actual sort columns**, not just `id`: if the user sorts by `created_at DESC`, the cursor is the last `created_at`, plus a unique tiebreaker (`id`) when the sort column is non-unique.
- **Dynamic sort plus cursor is hard**: with user-driven multi-column sort (`?sort=createdAt:desc,price:asc`), the cursor must encode every sort column as a tuple and its structure changes per combination. Most APIs reserve cursor for fixed sort (feeds, audit logs) and fall back to `OFFSET` for dynamic sort (search/filter dashboards).

## Page vs Slice vs List

| Aspect            | `Page<T>`             | `Slice<T>`              | `List<T>`              |
|-------------------|-----------------------|-------------------------|------------------------|
| COUNT query fired | Yes                   | No                      | No                     |
| Knows total pages | Yes                   | `hasNext()` only        | No                     |
| Internal trick    | Separate `COUNT(*)`   | Fetches `LIMIT + 1` rows | Plain query           |
| Performance       | Slightly heavier      | Lighter                 | Lightest               |
| Use case          | UI needs total/page count | Infinite-scroll UIs | Items, no pagination metadata |

## Q&A

1. **`Page<T>` vs `Slice<T>`, when to use which?**
`Page` fires an extra `COUNT(*)` so it knows `getTotalElements()` and `getTotalPages()`. `Slice` skips the count and fetches `LIMIT + 1` rows to learn whether another page exists. Use `Slice` for infinite-scroll UIs and `Page` when you need total counts.

2. **Why is sorting recommended with pagination even though it is optional?**
Without `ORDER BY`, row order is undefined, so results can shift between pages as data changes or even between executions. A stable sort (ideally including the primary key as a tiebreaker) guarantees consistent paging.

3. **Is `Pageable.pageNumber` zero-based or one-based?**
Zero-based. `PageRequest.of(0, 10)` returns the first 10 rows.

4. **Method-name sorting (`findAllByOrderByNameAsc`) vs the `Sort` parameter?**
`Sort` is almost always better: it is dynamic, supports multiple fields, and keeps method names short. Use `OrderBy` in the name only when a method always needs the same fixed sort.

5. **What is the problem with `OFFSET`-based pagination on large tables?**
`OFFSET N` forces the database to scan and discard N rows before returning the page, so cost grows linearly with depth. For deep pagination use keyset (cursor) pagination (`WHERE id > :lastSeenId ORDER BY id LIMIT N`): constant cost and stable across inserts.

6. **When would you choose cursor over OFFSET pagination, and what does the cursor encode?**
Cursor pagination has constant cost regardless of depth, so use it for deep paging, infinite scroll, feeds, and audit timelines. The cursor encodes the last seen sort value(s) plus a unique tiebreaker (`id`) when the sort field is non-unique. It pairs cleanly with a fixed sort; with dynamic sort the cursor structure changes per query, so most APIs fall back to `OFFSET` there. Spring Data 3.1+ provides `KeysetScrollPosition` and `Window<T>`.

7. **If a user binds `Sort` directly from a request parameter, what is the security risk?**
`Sort.by(field)` accepts any property name, including ones the API did not intend to expose (such as `passwordHash`). Validate the sort field against an allow-list before constructing the `Sort`.

## Quick Revision Cheat Sheet

| Concept                          | Remember                                                       |
|----------------------------------|----------------------------------------------------------------|
| `Sort` parameter                 | Dynamic, multi-field; preferred over `OrderBy` in method names |
| `PageRequest.of(page, size)`     | Page number is zero-based                                      |
| `Page<T>`                        | Items + total count; fires an extra `COUNT(*)` query          |
| `Slice<T>`                       | No count; fetches `LIMIT + 1` for `hasNext()`; infinite scroll |
| `List<T>`                        | Items only, no pagination metadata                            |
| `OFFSET` paging                  | Cost grows with depth; fine for shallow/admin pages           |
| Keyset (cursor) paging           | Constant cost; `WHERE id > :last ORDER BY id`; needs a stable sort |
| `Window<T>` / `ScrollPosition`   | Spring Data 3.1+ built-in keyset scrolling                     |
| Sort from request                | Validate the field against an allow-list                       |
