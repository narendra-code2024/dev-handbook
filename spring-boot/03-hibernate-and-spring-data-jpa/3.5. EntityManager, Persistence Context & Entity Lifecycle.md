The `EntityManager` is JPA's gateway to the database; the persistence context it manages is an in-memory cache of entity instances whose states and changes Hibernate tracks for you.

---

## EntityManager and Persistence Context

`EntityManager` is the main JPA interface for interacting with the database. It handles `persist`, `find`, `remove`, and query creation, and manages the persistence context.

The persistence context is the in-memory cache of managed entity instances associated with an `EntityManager`, also known as the first-level cache (L1):

- One persistence context per `EntityManager`.
- Stores all entities that are currently managed.
- Guarantees one instance per primary key within its scope (entity identity).
- Automatically tracks changes (dirty checking) and synchronizes them on flush.

```java
Employee emp  = entityManager.find(Employee.class, 1L);
Employee emp2 = entityManager.find(Employee.class, 1L);
// emp == emp2 → true (same reference, returned from the L1 cache)
```

> **Note**: in Spring Boot you rarely call `EntityManager` directly; `repository.findById(id)` calls `EntityManager.find(...)` internally, with the same identity guarantee and L1 behavior.

### The Factory and EntityManager Hierarchy

Spring Boot manages a single application-wide `EntityManagerFactory` per data source. It produces short-lived `EntityManager` instances on demand, typically one per `@Transactional` method.

| Component              | Count                                       | Scope                          |
|------------------------|---------------------------------------------|--------------------------------|
| `EntityManagerFactory` | 1 per data source (singleton bean)          | Application lifetime           |
| `EntityManager`        | Many, one per `@Transactional` unit of work | Lives only during the transaction |
| Persistence context    | 1 per `EntityManager`                       | Same as the `EntityManager`    |

Two concurrent requests running `@Transactional` methods get two separate `EntityManager`s with two separate L1 caches; they do not share state.

## Entity Lifecycle States

A JPA entity moves through four states.

### Transient (New)

Just created with `new`, not associated with an `EntityManager`, no row in the database.

```java
Employee emp = new Employee();   // transient
```

### Persistent (Managed)

Associated with the persistence context and tracked; field changes synchronize to the database automatically on flush.

```java
entityManager.persist(emp);                                  // transient → persistent
Employee found = entityManager.find(Employee.class, 1L);     // also persistent
```

### Detached

Was persistent, but the context is no longer tracking it (transaction ended, `clear()`, or explicit `detach()`); field changes are not propagated.

```java
entityManager.detach(emp);   // persistent → detached
```

### Removed

Marked for deletion; the actual `DELETE` runs on commit/flush.

```java
entityManager.remove(emp);   // persistent → removed
```

> **Note**: the examples above use `EntityManager` to show transitions explicitly. Day-to-day Spring Boot code uses `userRepository.save(emp)` (persist for new entities, merge for detached) and `userRepository.delete(emp)` (remove), which call the `EntityManager` methods underneath; detach happens automatically when the `@Transactional` method returns.

## Dirty Checking

While an entity is persistent you do not call `update()` or `save()`. At commit time Hibernate compares the original snapshot to the current state and emits an `UPDATE` for any changed fields.

```java
@Transactional
public void renameEmployee(Long id, String newName) {
    Employee emp = entityManager.find(Employee.class, id);
    emp.setName(newName);
    // no save/update call; dirty checking emits the UPDATE on commit
}
```

---

## Flush vs Commit

- **`flush()`**: synchronizes the persistence context with the database by executing pending SQL. It does not commit, so changes can still be rolled back.
- **`commit()`**: permanently persists the changes and ends the transaction.

Spring calls `flush()` automatically before commit; you rarely call it yourself (occasionally to surface constraint violations early in tests).

## persist vs merge vs save

All three save an entity, but they handle different starting states; getting them wrong silently drops your changes.

### persist(entity)

For new entities with no ID yet (just created with `new`).

```java
Employee emp = new Employee("Alice", 50000);   // transient, no id
entityManager.persist(emp);
// emp is now managed; INSERT runs on flush; emp.getId() is populated
// you can keep using emp directly, it is the same object, now managed
```

- Throws if the entity already has a persisted ID.
- Returns `void`, but the argument is mutated in place (ID populated, becomes managed).

### merge(entity)

For detached entities, previously managed but the transaction has ended (for example, loaded in one transaction and updated in another).

```java
Employee emp = ...;                       // detached
emp.setName("Bob");
Employee managed = entityManager.merge(emp);
// merge COPIES emp's state into a NEW managed copy
// `managed` is now in the persistence context
// `emp` stays detached, it never becomes managed
```

Common bug, ignoring the return value:

```java
entityManager.merge(emp);                 // return value not captured
emp.setName("Charlie");                   // invalid: won't persist, emp is still detached
```

Assign and use the return value instead:

```java
Employee managed = entityManager.merge(emp);
managed.setName("Charlie");               // OK: persists, managed is in the context
```

### save(entity)

`JpaRepository.save()` picks automatically:

- If the entity is new (`id == null`, or `@Version` is null when present), it calls `persist`.
- Otherwise it calls `merge`.

```java
User saved = userRepository.save(user);
```

Always assign and use the return value. For new entities `saved == user` (same object); for detached entities `saved` is the managed copy while `user` stays detached, so using `saved` avoids the silent-drop bug above.

## Entity equals / hashCode

Entities are stored in `Set`s and `Map`s (especially in `@ManyToMany` and bidirectional `@OneToMany` collections), so their identity contract matters.

- **Do not use Lombok `@Data` on entities**: it generates `equals`/`hashCode` over all fields including lazy collections, so a `Set.add` triggers lazy loads and can `StackOverflowError` on bidirectional graphs.
- **Do not use the auto-generated ID in `equals` directly**: two transient instances both have `id == null` and would compare equal.
- Safest pattern: a business key (natural unique identifier) when one exists; otherwise an `equals` that returns `true` only when both IDs are non-null and equal, plus a constant `hashCode` (such as `getClass().hashCode()`).

## First-Level vs Second-Level Cache

| Aspect       | First-Level (L1)                  | Second-Level (L2)                      |
|--------------|-----------------------------------|----------------------------------------|
| Layer        | JPA persistence context           | JPA, via a pluggable cache provider    |
| Scope        | Per `EntityManager` / transaction | Shared across sessions / requests      |
| Stores       | Managed entities (1 per PK)       | Entity rows (deconstructed)            |
| Enabled      | Always on                         | Opt-in, must be configured             |
| Backends     | Built-in                          | Ehcache, Caffeine, Hazelcast, Infinispan, Redis |
| Use case     | Identity guarantee in a transaction | Cross-request entity caching         |
| Modern usage | Universal                         | Rare in microservices (cache coherence issues) |

> **Note**: do not confuse JPA L2 with Redis-via-`@Cacheable`. Most teams use Redis as an application-level cache for method results (DTOs, API responses) via Spring Cache annotations, a different layer than JPA L2, which caches entity rows. See [11.3 Redis Cache in Spring Boot](<../11-caching-and-concurrent-transaction-management/11.3. Redis Cache in Spring Boot.md>).

## LazyInitializationException

Thrown when code accesses a lazy-loaded relationship on a detached entity; the persistence context is closed, so Hibernate has no session to fire the SELECT.

Common causes:

- Returning an entity from the service layer and accessing lazy fields in the controller or view.
- Calling `entityManager.clear()` mid-flow.
- Missing `@Transactional` on the calling method (see [3.8 Transactions](<3.8. Transactions.md>)).

Fixes (load the data before the context closes):

- `JOIN FETCH` in JPQL.
- `@EntityGraph` on the repository method.
- DTO projection.
- Keep the read inside an `@Transactional` method.

See [3.9 N+1 Query Problem](<3.9. N+1 Query Problem.md>) for the related fetch-strategy discussion.

## Q&A

1. **What is the persistence context?**
An in-memory cache of managed entities tied to an `EntityManager`. It guarantees a single instance per primary key, tracks field changes via dirty checking, and synchronizes them on flush. It is also called the first-level cache.

2. **Walk through the four entity lifecycle states.**
Transient: just created, not managed. Persistent: tracked by the context, changes flushed automatically. Detached: was persistent but the context is closed, changes ignored. Removed: marked for deletion, the `DELETE` fires on commit.

3. **What is dirty checking?**
Hibernate compares each managed entity's current field values to the snapshot taken when it was loaded; any differences produce an `UPDATE` at flush time, so you do not call `save()` for already-managed entities.

4. **Why does `LazyInitializationException` happen?**
The entity is detached (context closed) and the code touches a lazy relationship, so Hibernate has no session to fire the SELECT. Fix by loading eagerly via `JOIN FETCH` / `@EntityGraph` / DTO projection, or by keeping the access inside the transaction.

5. **`flush()` vs `commit()`?**
`flush()` pushes pending SQL to the database but stays inside the transaction (changes can still be rolled back); `commit()` makes the changes permanent and closes the transaction. Spring calls `flush()` automatically before commit.

6. **First-level vs second-level cache?**
L1 is the persistence context: per `EntityManager`, on by default, cannot be disabled. L2 is an optional shared cache across sessions (Ehcache, Caffeine) that avoids repeated reads of the same entity from disk.

7. **`persist` vs `merge` vs `save`?**
`persist` moves transient to managed (`void` return). `merge` copies a detached entity's state into a managed copy and returns it; the argument stays detached. Spring Data's `save` calls `persist` for new entities and `merge` otherwise; always use the returned value.

8. **Why is Lombok `@Data` dangerous on JPA entities?**
`@Data` generates `equals`/`hashCode` over all fields including lazy collections, so a `Set.add` lazily loads those collections and can `StackOverflowError` on bidirectional graphs. Use `@Getter`/`@Setter` only and write `equals`/`hashCode` deliberately (business key or ID-with-non-null guard).
