Cascade controls which JPA operations on a parent propagate to its children; `orphanRemoval` extends that to collection edits, and soft-delete patterns replace physical deletion with a marker column.

---

## Cascade

Cascade defines which JPA operations on a parent entity automatically propagate to its related entities.

```java
@Entity
public class Order {

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
    private List<OrderItem> items;
}
```

Saving, deleting, or updating the `Order` now propagates to its `OrderItem`s automatically, with no manual loop.

### Cascade Types

| Type                  | Behavior                                          |
|-----------------------|---------------------------------------------------|
| `CascadeType.PERSIST` | Save parent → save children                       |
| `CascadeType.MERGE`   | Merge parent → merge children                     |
| `CascadeType.REMOVE`  | Delete parent → delete children (use carefully)   |
| `CascadeType.REFRESH` | Reload parent → reload children                   |
| `CascadeType.DETACH`  | Detach parent → detach children                   |
| `CascadeType.ALL`     | All of the above                                  |

### JPA Cascade vs Database Cascade

- **JPA cascade**: handled by Hibernate at the application layer; respects the entity lifecycle.
- **Database cascade** (`ON DELETE CASCADE`): handled by the database engine; Hibernate has no visibility into it.

Use JPA cascade for object-level control, and add DB-level cascade only when you need the database to enforce it independently of the application.

## Orphan Removal

`orphanRemoval = true` means that when a child is removed from the parent's collection (or its parent reference is set to `null`), Hibernate deletes that child from the database.

```java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private List<OrderItem> items;
```

What happens:

- Save order → items saved (`CascadeType.PERSIST`).
- Delete order → items deleted (`CascadeType.REMOVE`).
- Remove an item from the `items` list → that item's row is deleted (`orphanRemoval`).

Orphan removal works only with `@OneToMany` and `@OneToOne`.

### Why "Orphan"

A child removed from the parent's collection no longer has a parent, so it becomes an orphan. With `orphanRemoval = true`, Hibernate deletes orphans; without it they stay in the database with a (possibly null) foreign key.

```
Order ── Item1, Item2

// remove Item1 from order.items
Order ── Item2

// Item1 is now an orphan
//   orphanRemoval = true  → DELETE FROM order_item WHERE id = Item1
//   orphanRemoval = false → row remains, FK may go null
```

### CascadeType.REMOVE vs orphanRemoval

| Action                        | `cascade = REMOVE` | `orphanRemoval = true` |
|-------------------------------|--------------------|------------------------|
| Delete parent                 | Children deleted   | Children deleted       |
| Remove child from collection  | Child stays        | Child deleted          |

### Requirements and When to Use It

- Must run within an active transaction (the persistence context must be open).
- Both sides of a bidirectional relationship must be kept in sync in code.

Use it when the child cannot exist without the parent (`Order` to `OrderItem`, `Blog` to `Comment`, `Invoice` to `InvoiceLine`). Avoid it when the child can exist independently (`Student` and `Course` via `@ManyToMany`, `Employee` to `Department`).

## Soft Delete Pattern

Sometimes physical deletion is wrong, for regulatory requirements, audit trails, or recoverability. Soft delete keeps the row but marks it deleted via a column. Spring Data JPA has no built-in soft delete, so use Hibernate's `@SQLDelete` + `@SQLRestriction`:

```java
@Entity
@SQLDelete(sql = "UPDATE employees SET deleted_at = NOW() WHERE id = ?")
@SQLRestriction("deleted_at IS NULL")
public class Employee {

    @Id
    @GeneratedValue
    private Long id;

    private String name;
    private Instant deletedAt;
}
```

- **`@SQLDelete`**: overrides the DELETE statement, so `repository.delete()` (and `entityManager.remove()`) runs your UPDATE instead.
- **`@SQLRestriction`**: adds `WHERE deleted_at IS NULL` to every query automatically (it replaced the deprecated `@Where` in Hibernate 6.3).

### What Does and Doesn't Soft Delete

| Operation                                                            | Soft delete?                                                            |
|----------------------------------------------------------------------|-------------------------------------------------------------------------|
| `delete(entity)` / `deleteById(id)` / `entityManager.remove()`       | Yes, auto via `@SQLDelete`                                              |
| `findAll()` / `findById()` and other queries                        | Yes, auto-filtered via `@SQLRestriction`                               |
| Cascade delete to child entities                                     | No; children physically deleted unless they also have `@SQLDelete`     |
| Native query                                                         | No; bypasses `@SQLRestriction`, add `WHERE deleted_at IS NULL`         |
| Bulk `@Modifying` `DELETE`                                           | No; bypasses `@SQLDelete`, use `UPDATE ... SET deleted_at = NOW()`     |
| Restoring a soft-deleted row                                         | No `JpaRepository` method does this; use native `UPDATE ... SET deleted_at = NULL` |
| Unique constraint on a soft-deleted row                              | Deleted row still occupies the slot; include `deleted_at` in the constraint or use a partial index (PostgreSQL) |

### Alternative: Archive Table

For high-volume tables, soft delete bloats the main table and slows queries, since every query carries the `deleted_at IS NULL` filter. Move deleted rows to a separate `archive_employees` table via a scheduled job, which keeps the live table fast while preserving history.

### Hibernate `@SoftDelete`

Hibernate 6.4 added a native `@SoftDelete` annotation that replaces the `@SQLDelete` + `@SQLRestriction` combo and lets Hibernate manage the column.

```java
@Entity
@SoftDelete(strategy = SoftDeleteType.DELETED) // boolean column, true when removed
public class Employee {

    @Id
    @GeneratedValue
    private Long id;

    private String name;
    // Hibernate manages the soft-delete column; no field to declare
}
```

Strategies:

- `SoftDeleteType.ACTIVE`: boolean column, `true` when the row is active (the default).
- `SoftDeleteType.DELETED`: boolean column, `true` when the row is deleted.
- `SoftDeleteType.TIMESTAMP` (Hibernate 7.0+): stores the deletion timestamp, `NULL` when active.

> **Note**: in Hibernate 6.4 through 6.6, `@SoftDelete` supports only the boolean strategies `ACTIVE` and `DELETED`. Timestamp-based soft delete (`SoftDeleteType.TIMESTAMP`) was added in Hibernate 7.0 (Spring Boot 3.5+); on earlier versions use `@SQLDelete` + `@SQLRestriction` for a timestamp column.

| Aspect             | `@SQLDelete` + `@SQLRestriction`        | `@SoftDelete`                          |
|--------------------|-----------------------------------------|----------------------------------------|
| Hibernate version  | 5.x+ (`@SQLRestriction` since 6.3)      | 6.4+ (boolean); `TIMESTAMP` in 7.0+    |
| DELETE override    | Manual SQL string                       | Auto-generated                         |
| Query filter       | Manual `@SQLRestriction`                | Auto-applied                           |
| Column declaration | Declare the flag/timestamp field        | Hibernate manages the column           |
| Strategies         | Any, via custom SQL                     | `ACTIVE`, `DELETED`; `TIMESTAMP` (7.0+) |
| Cascade behavior   | Children need their own annotation      | Children need their own annotation     |

On Spring Boot 3.3+ prefer `@SoftDelete` with a boolean strategy for less manual SQL; for a timestamp column, use `@SQLDelete` + `@SQLRestriction` until you are on Hibernate 7.0+.

## Q&A

1. **`CascadeType.REMOVE` vs `orphanRemoval = true`, what is the difference?**
`REMOVE` propagates parent deletion to children. `orphanRemoval` additionally deletes a child the moment it is removed from the parent's collection (or its parent reference is nulled). Use `orphanRemoval` for parent-owned children whose lifecycle is bound to the parent.

2. **Why is `CascadeType.ALL` considered risky?**
It includes `REMOVE`, so deleting a parent silently deletes everything it references, which is easy to do unintentionally across long entity graphs. Prefer the minimal subset (`PERSIST`, `MERGE`) and add `REMOVE` deliberately.

3. **JPA cascade vs database `ON DELETE CASCADE`, which should you use?**
They operate at different layers. JPA cascade keeps the persistence context consistent and fires entity lifecycle callbacks; DB-level cascade enforces the rule even when rows are deleted outside the application. Use JPA cascade as the primary mechanism and add DB-level cascade only when the database must enforce integrity on its own.

4. **Why doesn't `orphanRemoval` work on `@ManyToMany`?**
In a many-to-many relationship the child has multiple potential parents, so removing one association does not make it an orphan. JPA allows `orphanRemoval` only on `@OneToMany` and `@OneToOne`, where ownership is clear.
