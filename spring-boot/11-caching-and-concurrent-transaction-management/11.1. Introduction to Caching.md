Caching stores frequently accessed data in a fast storage layer so future requests are served quicker than fetching from the original source every time.

```
Without caching:
  Request → DB query (slow, every time)

With caching:
  First request  → DB query → store result in cache
  Next requests  → return from cache (fast, no DB hit)
```

---

## Why Cache?

- Reading from memory is faster than fetching from a database.
- Reduces costly backend and database requests.
- Improves application performance and response time.
- Helps the application scale under high traffic.

---

## Caching at Different Layers

```
User Request
  │
  ▼
DNS Cache (browser/OS)
  │  Domain → IP resolved once, cached for future requests
  │
  ▼
Web Cache (CDN)
  │  Static content (images, CSS, JS) served from edge servers
  │  closer to the user, not from the origin server
  │
  ▼
Application Cache (Redis, Memcached)
  │  Frequently accessed data and computation results
  │  stored in memory, avoids repeated DB queries
  │
  ▼
Database Cache (query cache, buffer pool)
     The DB's own internal caching layer (low level),
     managed by the database engine itself
```

| Layer       | What's Cached                               | Implemented By                             |
| ----------- | ------------------------------------------- | ------------------------------------------ |
| DNS         | Domain to IP mapping                        | Browser, OS (first lookup only, then cached) |
| Web         | Static content (pages, images, assets)      | CDN (Cloudflare, AWS CloudFront)           |
| Application | Query results, computed data, API responses | Redis, Memcached, Spring Cache             |
| Database    | Query plans, frequently read rows           | Database engine internally                 |

> **Note**: this file focuses on application-level caching, holding data inside your Spring Boot app using Spring Cache and Redis.

## Caching Terminologies

### Cache Hit and Cache Miss

```
Request for data
  │
  ▼
Is it in the cache?
  ├── Yes → Cache Hit (return from cache, fast)
  └── No  → Cache Miss (fetch from DB, store in cache for next time)
```

### Cache Eviction Policies

When the cache is full and a new entry must be added, an eviction policy decides which existing entry is removed. LRU is the most commonly used.

| Policy                          | How It Decides                                             |
| ------------------------------- | --------------------------------------------------------- |
| LRU (Least Recently Used)       | Remove the entry not accessed for the longest time         |
| LFU (Least Frequently Used)     | Remove the entry accessed the fewest times                 |
| FIFO (First In First Out)       | Remove the oldest entry by insertion                       |
| TTL-based                       | Remove entries that have expired (based on time-to-live)   |

### Cache Expiry and TTL

TTL (time-to-live) is how long a cached entry stays valid before it is automatically removed. Without it, stale data could live in the cache forever while the underlying data in the DB has changed.

```
Cache entry created at 10:00 AM with TTL = 5 minutes
  → Valid until 10:05 AM
  → After 10:05 AM → expired → next request is a cache miss → fresh data fetched
```

### Cache Loading Strategies

**Lazy loading**: the cache starts empty and data is loaded only when first requested. The first user pays the miss cost; everyone after gets it fast. This is the most common strategy.

```
App starts → cache is empty
  │
  ▼
First request: GET /api/categories
  → Cache miss → fetch from DB → store in cache → return (slow)
  │
  ▼
Second request: GET /api/categories
  → Cache hit → return from cache (fast)
```

**Eager loading (cache warming)**: pre-load frequently needed data into the cache at startup, before any requests arrive. Used for data you know will be requested often (categories, config, country lists), so no user ever hits a cold cache.

```
App starts → load categories, config, countries into cache
  │
  ▼
First request: GET /api/categories
  → Cache hit → fast (already loaded, no cold cache)
```

### Cache Size and Capacity

Cache memory is limited, so you cannot cache everything. Configure max entries or max memory to cap resource use; eviction policies kick in once the limit is reached.

## Q&A

1. **What is caching and why is it used?** Caching stores frequently accessed data in a fast storage layer (typically memory) so repeat requests skip the expensive source (DB, remote API). It reduces latency, lowers backend load, and helps the app scale.
2. **Cache hit vs cache miss?** A hit means the requested data was found in cache (fast path). A miss means it was not, so the app fetches from the source and typically populates the cache for next time.
3. **What is TTL and why does it matter?** TTL (time-to-live) is how long a cached entry is considered valid. Without it, stale data can live in the cache indefinitely even after the underlying source changes.
4. **Compare common eviction policies.** LRU evicts the entry not accessed for the longest time (most common). LFU evicts the least frequently accessed. FIFO evicts the oldest by insertion. TTL-based evicts expired entries regardless of access pattern.
5. **Lazy loading vs cache warming?** Lazy loading populates the cache on first request (first user pays the miss cost). Cache warming pre-loads known hot data at startup so no user hits a cold cache, used for catalogs, config, and reference lists.
6. **Where does application-level caching sit relative to other cache layers?** Between web/CDN caches (static assets) above and the DB's own buffer pool below. It holds processed query results and computed data in memory (Redis, Memcached, Spring Cache).
