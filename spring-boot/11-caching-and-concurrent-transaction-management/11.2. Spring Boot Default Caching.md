## Spring Boot Cache Abstraction

Spring Boot provides a Cache Abstraction API, a layer on top of different cache providers. You write the same annotations regardless of whether the underlying cache is in-memory, Redis, or something else, and you can swap the provider later by changing only the dependency and config.

By default (no extra dependencies), Spring uses a simple `ConcurrentHashMap` as the cache, just a `Map<key, value>` stored in memory.

```
Cache Abstraction API
  │
  ├── Default: ConcurrentHashMap (in-memory, single server)
  ├── Redis (distributed, shared across servers)
  ├── Caffeine (high-performance in-memory)
  └── Others (EhCache, Hazelcast, etc.)
```

---

## How It Works Internally

```
@Cacheable method called
  │
  ▼
Spring AOP intercepts the call (proxy)
  │
  ▼
CacheManager retrieves the Cache by name (e.g., "employees")
  │
  ▼
Cache checks: does this key exist?
  │
  ├── Hit → return cached value (method never executes)
  │
  └── Miss → execute the actual method
                │
                ▼
           Store result in cache (key → value)
                │
                ▼
           Return result to caller
```

The `CacheManager` manages multiple named caches; with the default provider each cache is a `ConcurrentMap<Object, Object>`.

---

## Enabling Caching

Add `@EnableCaching` to any configuration class. This registers a `CacheManager` and wires the AOP proxy; without it, the caching annotations do nothing.

```java
@Configuration
@EnableCaching
public class CacheConfig {
}
```

## Caching Annotations

### @Cacheable: Cache the Result

If the result is already cached, return it without executing the method. Otherwise execute the method and store the result.

```java
@Cacheable(cacheNames = "employees", key = "#id")
public EmployeeDto getEmployeeById(Long id) {
    // Runs only on a cache miss
    return employeeRepository.findById(id)
        .map(employeeMapper::toDto)
        .orElseThrow();
}
```

```
First call:  getEmployeeById(1L) → cache miss → DB query → store in cache
Second call: getEmployeeById(1L) → cache hit → return from cache (no DB)
Third call:  getEmployeeById(2L) → cache miss → DB query (different key)
```

The `key` SpEL expression controls what becomes the cache key; with no key, Spring uses all method arguments:

```java
@Cacheable(cacheNames = "employees", key = "#id")     // key = the id argument
@Cacheable(cacheNames = "employees", key = "#email")  // key = the email argument
@Cacheable(cacheNames = "employees")                  // key = all method arguments
```

> **Note**: prefer an explicit `key = "#..."` in production. The default `SimpleKeyGenerator` hashes all method arguments, which is easy to trip over when args include DTOs, pageables, or auth objects whose `equals`/`hashCode` do not match what you want as a cache key.

### @CachePut: Update the Cache

Always executes the method and updates the cache with the new result. Use it for writes where the cache should reflect the latest data.

```java
@CachePut(cacheNames = "employees", key = "#id")
public EmployeeDto updateEmployee(Long id, EmployeeDto dto) {
    // Always runs: updates DB and cache
    Employee employee = employeeRepository.findById(id).orElseThrow();
    employee.setFirstName(dto.getFirstName());
    return employeeMapper.toDto(employeeRepository.save(employee));
}
```

`@Cacheable` skips the method on a hit (read path); `@CachePut` always runs and writes the result back (write-through path):

| Dimension        | @Cacheable                  | @CachePut                      |
| ---------------- | --------------------------- | ------------------------------ |
| Method executes? | Only on cache miss          | Always                         |
| Purpose          | Read, avoid repeated fetches | Write, update cache after change |
| Use for          | GET operations              | UPDATE operations              |

### @CacheEvict: Remove from Cache

Removes entries from the cache, either a single key or the entire cache region. Use it when data is deleted or when you want to force a fresh fetch next time.

```java
@CacheEvict(cacheNames = "employees", key = "#id")
public void deleteEmployee(Long id) {
    employeeRepository.deleteById(id);   // cache entry for this id is removed
}

@CacheEvict(cacheNames = "employees", allEntries = true)
public void refreshAllEmployees() {
    // Clears the entire "employees" cache
}
```

## Which Layer to Cache?

You can place caching annotations on the controller, service, or repository; the service layer is the most common because it sits between controller and repository, so you cache the processed result that is ready to return.

| Layer      | Trade-off                                                            |
| ---------- | ------------------------------------------------------------------- |
| Service    | Most common; caches the processed, ready-to-return result           |
| Repository | Caches raw DB queries, but may cache data before business logic runs |
| Controller | Caches the final response, but tightly couples cache to the HTTP layer |

## Q&A

1. **What does `@EnableCaching` do?** It activates Spring's caching infrastructure: registers a `CacheManager` and wires the AOP proxy that intercepts `@Cacheable`, `@CachePut`, and `@CacheEvict` calls. Without it, the annotations are ignored.
2. **Difference between `@Cacheable` and `@CachePut`?** `@Cacheable` skips the method when the key is cached (read path); `@CachePut` always executes and writes the result back (write-through). Use `@Cacheable` for GETs, `@CachePut` for UPDATEs.
3. **When would you use `@CacheEvict(allEntries = true)`?** When a bulk operation invalidates the whole cache region (a full re-import, a schema change), so every entry under that cache name is cleared in one call.
4. **What is the default cache backing in Spring Boot?** A `ConcurrentHashMap`-backed in-memory cache. It is single-JVM only and does not survive restarts; swap to Redis or Caffeine for distributed or durable caching (see [11.3 Redis Cache in Spring Boot](<11.3. Redis Cache in Spring Boot.md>)).
5. **How is the cache key computed without an explicit `key`?** Spring builds it from all method arguments via `SimpleKeyGenerator` (single arg becomes that arg, multiple args become a composite `SimpleKey`). Prefer an explicit SpEL `key = "#id"` to avoid surprises.
6. **Which layer should hold cache annotations?** Typically the service layer (the processed, ready-to-return result). Repository caching risks caching raw rows; controller caching couples the cache to HTTP specifics.
