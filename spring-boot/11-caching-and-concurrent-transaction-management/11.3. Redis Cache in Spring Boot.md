The default Spring cache (`ConcurrentHashMap`) lives inside your application's memory, so it is lost on restart and cannot be shared across instances. Redis runs as a dedicated server, so the cache survives restarts and is shared by every app instance.

```
Default (ConcurrentHashMap):
  App Instance 1 → own cache (in memory)
  App Instance 2 → own cache (different data)
  App restarts → cache lost

Redis (dedicated server):
  App Instance 1 ──┐
                   ├──→ Redis Server (shared cache)
  App Instance 2 ──┘
  App restarts → cache survives (Redis is separate)
```

|                         | Default Cache            | Redis                                |
| ----------------------- | ------------------------ | ------------------------------------ |
| Storage                 | App memory               | Dedicated server                     |
| Survives restart        | No                       | Yes                                  |
| Shared across instances | No                       | Yes                                  |
| Distributed             | No                       | Yes                                  |
| Speed                   | Very fast (same process) | Fast (network call, still in-memory) |

## Serialization, the Common Error

Switching from the default cache to Redis usually surfaces a `SerializationException: Cannot serialize`. The default cache stores Java objects directly in memory, but Redis stores data over the network as bytes, so objects must be serialized to bytes and back. The fix is to make your DTOs serializable:

```java
@Data
@Builder
public class EmployeeDto implements Serializable {

    private static final long serialVersionUID = 1L;

    private Long id;
    private String firstName;
    private String lastName;
    private String email;
}
```

| Field                     | Purpose                                                                          |
| ------------------------- | -------------------------------------------------------------------------------- |
| `implements Serializable` | Marks the object as convertible to bytes                                          |
| `serialVersionUID`        | Version identifier; bump it when the class structure changes to invalidate old data |

> **Note**: without a `serialVersionUID`, changing the class (adding or removing fields) makes deserialization of old cached data fail with `InvalidClassException`.

## RedisCacheManager Configuration

Customize TTL, key prefix, and serialization through a `RedisCacheManager` bean:

```java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory) {

        RedisCacheConfiguration config = RedisCacheConfiguration
            .defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))
            .keySerializerPair(RedisSerializationContext.SerializerPair
                .fromSerializer(new StringRedisSerializer()))
            .valueSerializerPair(RedisSerializationContext.SerializerPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()))
            .prefixCacheNameWith("myapp:")
            .disableCachingNullValues();

        return RedisCacheManager.builder(connectionFactory)
            .cacheDefaults(config)
            .enableStatistics()
            .build();
    }
}
```

| Method                          | Purpose                                                                  |
| ------------------------------- | ------------------------------------------------------------------------ |
| `entryTtl(Duration)`            | How long cached entries live before expiring                              |
| `keySerializerPair(...)`        | `StringRedisSerializer` stores keys as readable strings                   |
| `valueSerializerPair(...)`      | `GenericJackson2JsonRedisSerializer` stores values as JSON                |
| `prefixCacheNameWith("myapp:")` | Prefixes all keys; useful when multiple apps share one Redis              |
| `disableCachingNullValues()`    | Do not cache null results                                                 |
| `enableStatistics()`            | Track cache hit/miss statistics                                          |

Using `GenericJackson2JsonRedisSerializer` (above) stores values as JSON instead of Java byte serialization, which is the recommended approach: DTOs no longer need `implements Serializable`, cached data is human-readable in Redis (`GET` shows JSON), and it tolerates non-breaking class changes far better than Java serialization.

## No Code Changes for Caching Logic

The `@Cacheable`, `@CachePut`, and `@CacheEvict` annotations from [11.2 Spring Boot Default Caching](<11.2. Spring Boot Default Caching.md>) stay identical; they do not care whether the underlying cache is `ConcurrentHashMap` or Redis. You change only the dependency and config, which is the point of the Cache Abstraction.

```java
// Same annotation works with the default cache and with Redis
@Cacheable(cacheNames = "employees", key = "#id")
public EmployeeDto getEmployeeById(Long id) {
    return employeeRepository.findById(id)
        .map(employeeMapper::toDto)
        .orElseThrow();
}
```

## Production Considerations

- **TTL is mandatory**: always set `entryTtl(...)` on the `RedisCacheConfiguration`; without it, stale entries can outlive their source of truth indefinitely. Tie the value to your data freshness SLA (5-30 min for catalog data, seconds for hot inventory).
- **Per-cache TTLs**: `RedisCacheManager.builder(cf).withCacheConfiguration("shortLived", shortConfig).withCacheConfiguration("longLived", longConfig)` gives each cache name its own TTL.
- **Manual invalidation alongside TTL**: time-based eviction is a safety net; combine it with explicit `@CacheEvict` on writes so updates show up immediately rather than after expiry.
- **Connection pooling**: Spring Boot ships Lettuce by default (non-blocking, thread-safe, a single multiplexed connection). Switch to Jedis with a pool (`spring.data.redis.client-type: jedis`) only for a specific reason; Lettuce handles most workloads.
- **Serializer choice**: prefer `GenericJackson2JsonRedisSerializer` over Java native (`JdkSerializationRedisSerializer`); it is readable in `redis-cli`, cross-language safe, and tolerant of non-breaking class changes.
- **Failover**: for high availability use Redis Sentinel or Cluster (`spring.data.redis.sentinel.*` / `cluster.*`). Treat the cache as a soft dependency so a Redis outage degrades latency rather than breaking the app.

## Q&A

1. **Why use Redis over the default in-memory cache?** Redis survives app restarts and is shared across instances, which is essential for multi-node deployments. The default `ConcurrentHashMap` cache is per-JVM and wiped on restart.
2. **What causes `SerializationException` when switching to Redis?** Redis stores bytes over the network, so cached objects must be serializable. Either implement `java.io.Serializable` on the DTO or configure a JSON serializer (`GenericJackson2JsonRedisSerializer`).
3. **Why is JSON serialization preferred over Java `Serializable`?** JSON values are human-readable in Redis, version-tolerant across class changes, and do not require DTOs to implement `Serializable`. Java byte serialization is brittle when fields change without bumping `serialVersionUID`.
4. **What is `serialVersionUID` and why does it matter?** A version identifier on `Serializable` classes. If you change the class structure and the old value remains, deserializing cached data throws `InvalidClassException`. Bump it to invalidate old data after breaking changes.
5. **Do the cache annotations change when moving to Redis?** No. The Cache Abstraction keeps them identical; only the dependency, `spring.cache.type`, and optionally the `RedisCacheManager` bean change.
6. **What does `prefixCacheNameWith("myapp:")` solve?** It namespaces keys so multiple apps sharing one Redis instance do not collide. Keys become `myapp:employees::1` instead of `employees::1`.
