A transaction is a logical unit of work that groups multiple database operations into one. Either all operations succeed (commit) or none of them do (rollback).

```
Transfer $100 from Alice to Bob:
  Step 1: Debit Alice  -$100
  Step 2: Credit Bob   +$100

Both must succeed or neither should happen.
If Step 2 fails after Step 1 → rollback → Alice gets her $100 back.
```

> **Reference**:
> - JPA persistence-context angle: [3.8 Transactions](<../03-hibernate-and-spring-data-jpa/3.8. Transactions.md>).
> - Spring `@Transactional` details: [11.6 Transactional Annotation in Spring Boot](<11.6. Transactional Annotation in Spring Boot.md>).

---

## Commit and Rollback

- **Commit**: all steps succeeded, so the changes are made permanent.
- **Rollback**: something failed, so everything is undone back to the initial state as if the transaction never happened.

```
Transaction starts
  │
  ├── All steps succeed → COMMIT (changes saved permanently)
  │
  └── Any step fails → ROLLBACK (all changes undone)
```

## Seeing It Live: Terminal Example

```sql
CREATE TABLE accounts (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50),
    amount DECIMAL(10, 2)
);

INSERT INTO accounts (name, amount) VALUES ('Alice', 1000.00);
INSERT INTO accounts (name, amount) VALUES ('Bob', 500.00);
```

**Successful transaction**:

```sql
BEGIN;
UPDATE accounts SET amount = amount - 100 WHERE name = 'Alice';
UPDATE accounts SET amount = amount + 100 WHERE name = 'Bob';
COMMIT;
-- Alice: 900, Bob: 600 (both changes saved)
```

**Failed transaction (automatic rollback)**:

```sql
BEGIN;
UPDATE accounts SET amount = amount - 100 WHERE name = 'Alice';

SELECT * FROM accountsssss;   -- typo: relation does not exist
-- ERROR: current transaction is aborted

COMMIT;
-- Even COMMIT rolls back here; Alice still has her original amount
```

**Manual rollback**:

```sql
BEGIN;
UPDATE accounts SET amount = amount - 100 WHERE name = 'Alice';
ROLLBACK;
-- Alice still has her original amount
```

> **Note**: once any statement fails inside a transaction, the whole transaction is marked aborted, so even `COMMIT` triggers a rollback at that point.

## ACID Properties

| Property    | What It Means                                                          | Example                                                       |
| ----------- | --------------------------------------------------------------------- | ------------------------------------------------------------ |
| Atomicity   | All or nothing: every operation succeeds or none do                    | Bank transfer: debit and credit both happen or neither       |
| Consistency | The DB moves from one valid state to another, with all rules upheld    | Cannot place an order if stock is 0, even mid-transaction     |
| Isolation   | Concurrent transactions do not interfere with each other               | Two people cannot book the same airline seat simultaneously   |
| Durability  | Once committed, changes are permanent even if the system crashes        | A confirmed payment survives a server restart                |

```
Without ACID:
  Alice -$100 → server crashes before crediting Bob → $100 disappears

With ACID:
  Alice -$100 → server crashes before crediting Bob
  → transaction never committed → ROLLBACK → Alice still has her $100
```

## Trade-offs

- **Advantages**: data integrity (no corruption), predictable and reliable execution, concurrency control so multiple users do not conflict, and fault tolerance across failures. This is critical wherever money or limited resources are involved (banking, reservations, e-commerce, inventory).
- **Disadvantages**: performance overhead from the guarantees, added implementation complexity, scalability challenges in distributed systems, deadlock potential from locking, and reduced concurrency under strict isolation.

---

## When ACID Isn't Necessary

Not every system needs strict ACID. Some use eventual consistency: data becomes consistent eventually, not immediately, trading immediate correctness for performance and scalability.

| Needs ACID            | Can Use Eventual Consistency |
| --------------------- | ---------------------------- |
| Banking / payments    | Caching systems              |
| Reservation systems   | Analytics / reporting        |
| E-commerce orders     | Social media feeds           |
| Inventory management  | Large-scale blogging         |

> **Note**: MongoDB uses eventual consistency by default; writes may not be immediately visible to all readers but converge eventually.

> **Note**: the CAP theorem says a distributed system can guarantee at most two of Consistency, Availability, and Partition-tolerance. Strict ACID across nodes (CP) hurts availability under network splits; eventual consistency (AP) stays responsive but defers convergence. Choose based on what your domain cannot tolerate losing.

## Q&A

1. **What does ACID stand for?** Atomicity (all-or-nothing), Consistency (valid state to valid state), Isolation (concurrent transactions do not interfere), Durability (committed data survives crashes).
2. **Difference between commit and rollback?** Commit makes all changes in the transaction permanent. Rollback undoes them, leaving the DB exactly as it was before the transaction started.
3. **What happens if a statement fails inside a `BEGIN`/`COMMIT` block?** The transaction is marked aborted, so subsequent statements (including `COMMIT`) effectively roll back; no partial changes survive.
4. **Atomicity vs Consistency, aren't they the same?** No. Atomicity is the transaction's all-or-nothing behavior. Consistency is constraint preservation: referential integrity, check constraints, and business invariants must hold before and after.
5. **When is strict ACID overkill?** For analytics, social feeds, large-scale blogs, and caching layers, where eventual consistency is acceptable and throughput matters more than immediate correctness.
6. **What is the relationship between ACID and `@Transactional`?** `@Transactional` is Spring's way to start, commit, and roll back transactions; the database enforces the ACID guarantees. Spring just defines the boundary (see [11.6 Transactional Annotation in Spring Boot](<11.6. Transactional Annotation in Spring Boot.md>)).
