Multiple transactions running at the same time can interfere with each other. Open two terminal windows connected to the same database (Transaction A and Transaction B hitting the same data) to reproduce the problems below.

## Three Problems That Can Occur

### Dirty Read

Transaction B reads data that Transaction A has not committed yet. If A rolls back, B has read a value that never actually existed.

```
Transaction A                    Transaction B
     │                                │
T0:  UPDATE accounts                  │
     SET amount = 900                 │
     WHERE id = 1;                    │
     (not committed yet)              │
     │                                │
T1:  │                           SELECT amount FROM accounts
     │                           WHERE id = 1;
     │                           → sees 900 (uncommitted!)
     │                                │
T2:  ROLLBACK;                        │
     (amount is back to 1000)    B now has 900, a value that
                                 never actually existed
```

### Non-Repeatable Read

Transaction A reads the same row twice and gets different values because Transaction B committed a change in between. The same query, in the same transaction, returns a different result.

```
Transaction A                    Transaction B
     │                                │
T0:  SELECT amount FROM accounts      │
     WHERE id = 1; → sees 1000        │
     │                                │
T1:  │                           UPDATE accounts SET amount = 900
     │                           WHERE id = 1; COMMIT;
     │                                │
T2:  SELECT amount FROM accounts      │
     WHERE id = 1; → sees 900         │
```

### Phantom Read

Transaction A runs the same query twice and gets different rows because Transaction B inserted or deleted rows in between; a "phantom" row appears.

```
Transaction A                    Transaction B
     │                                │
T0:  SELECT * FROM accounts           │
     WHERE amount < 1000;             │
     → returns 3 rows                 │
     │                                │
T1:  │                           INSERT INTO accounts
     │                           VALUES ('New User', 500); COMMIT;
     │                                │
T2:  SELECT * FROM accounts           │
     WHERE amount < 1000;             │
     → returns 4 rows (new row!)      │
```

## Lost Update Problem

Two transactions read the same value and both update it, so one update is overwritten. This is the core motivation for isolation levels and locking.

```
Account X = 100

Transaction A (credit ₹15)            Transaction B (debit ₹25)
     Read(X) → 100                          │
     X = 100 + 15 = 115                      │
     │                                  Read(X) → 100
     │                                  X = 100 - 25 = 75
     │                                  WRITE(X) → 75
     WRITE(X) → 115                          │

Final X = 115, incorrect (should be 90 = 100 + 15 - 25)
Transaction B's update is lost.
```

## Isolation Levels

Isolation levels control how much one transaction can see of another's uncommitted or committed changes. Higher isolation means fewer problems but slower performance.

### Read Uncommitted (Lowest)

Transactions can see uncommitted changes from others. All problems are possible (dirty, non-repeatable, phantom reads); rarely used.

```sql
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

### Read Committed (PostgreSQL Default)

Transactions only see committed changes, so no dirty reads. Non-repeatable and phantom reads can still happen.

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SHOW transaction_isolation;   -- check current level
```

```
T1: UPDATE amount = 900 WHERE id = 1   (not committed)
T2: SELECT amount WHERE id = 1         → still sees 1000
T1: COMMIT
T2: SELECT amount WHERE id = 1         → now sees 900
```

### Repeatable Read (MySQL Default)

Once a transaction reads a value, it sees the same value throughout, even if another transaction commits a change. T1 works from a consistent snapshot taken at its start; if it then updates a row another transaction already changed, it gets a serialization error instead of causing a lost update.

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

```
T1: SELECT amount WHERE id = 1  → sees 1000
T2: UPDATE amount = 900 WHERE id = 1; COMMIT;
T1: SELECT amount WHERE id = 1  → still sees 1000 (snapshot)
T1: UPDATE amount WHERE id = 1  → ERROR: could not serialize access
```

### Serializable (Highest)

Transactions behave as if they ran one after another. Maximum safety, lowest performance. Even if T1 started first, if T2 finished first and a conflict is detected, T1 is rolled back and must retry against fresh data.

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

---

## Isolation Levels Summary

| Level            | Dirty Read | Non-Repeatable Read | Phantom Read | Performance |
| ---------------- | ---------- | ------------------- | ------------ | ----------- |
| Read Uncommitted | Possible   | Possible            | Possible     | Fastest     |
| Read Committed   | Prevented  | Possible            | Possible     | Fast        |
| Repeatable Read  | Prevented  | Prevented           | Possible*    | Moderate    |
| Serializable     | Prevented  | Prevented           | Prevented    | Slowest     |

> **Note**: * Repeatable Read prevents phantoms in PostgreSQL (stricter than the SQL spec) but not by spec; MySQL's InnoDB typically prevents them via gap locks.

---

## PostgreSQL vs MySQL

|                                 | PostgreSQL                                                | MySQL (InnoDB)                                  |
| ------------------------------- | --------------------------------------------------------- | ----------------------------------------------- |
| Default level                   | Read Committed                                            | Repeatable Read                                 |
| How Serializable works          | Snapshot Isolation (SSI): no locks, detects and aborts conflicts | Row/range locks: transactions wait for locks    |
| Dirty Read at Read Uncommitted  | Not possible (PG treats it as Read Committed)             | Possible                                        |
| Phantom Read at Repeatable Read | Not possible (PG prevents it)                             | Possible by spec, prevented via gap locks        |
| Conflict handling               | Detects and aborts conflicting transactions               | Transactions wait (can deadlock)                |

PostgreSQL is optimistic: it lets transactions run concurrently and aborts on conflict. MySQL is pessimistic: it locks rows and makes transactions wait. PostgreSQL's approach generally gives better concurrency because transactions do not block each other.

## Checking and Setting the Isolation Level

```sql
-- PostgreSQL
SHOW transaction_isolation;            -- check
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- queries here
COMMIT;

-- MySQL
SELECT @@transaction_isolation;        -- check
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

Most applications run on Read Committed (a good balance); use Serializable for financial or critical data, and Repeatable Read for high-read, low-write workloads that need consistent reads.

> **Reference**: in Spring Boot you rarely set isolation manually; `@Transactional` handles it. See [11.6 Transactional Annotation in Spring Boot](<11.6. Transactional Annotation in Spring Boot.md>).

## Q&A

1. **Dirty read vs non-repeatable read vs phantom read?** Dirty read: reading another transaction's uncommitted changes. Non-repeatable read: same row and query, different value due to a committed update mid-transaction. Phantom read: same range query returns different rows due to a committed insert/delete.
2. **What is the lost update problem?** Two transactions read the same value, both compute updates from it, and the second write overwrites the first, losing the first transaction's effect. Solved by Serializable isolation, optimistic locking (`@Version`), or pessimistic locking (`SELECT ... FOR UPDATE`).
3. **Default isolation level in PostgreSQL vs MySQL?** PostgreSQL: Read Committed. MySQL (InnoDB): Repeatable Read.
4. **How does PostgreSQL implement Serializable differently from MySQL?** PostgreSQL uses Snapshot Serializable Isolation (SSI): transactions do not block, conflicts are detected and the conflicting transaction is aborted. MySQL uses row/range locks: transactions wait, with deadlock potential.
5. **Which isolation level prevents phantom reads?** Serializable in standard SQL. PostgreSQL's Repeatable Read also prevents them; MySQL's does not by spec but typically does in practice via gap locks.
6. **Trade-off of higher isolation?** Stronger guarantees but lower throughput: more locking, more conflict aborts, more retries. Most apps run on Read Committed; reach for Serializable only when concurrent-write correctness demands it.
