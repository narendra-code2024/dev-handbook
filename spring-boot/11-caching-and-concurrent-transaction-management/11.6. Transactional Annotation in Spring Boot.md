`@Transactional` defines a transaction boundary around a method: Spring opens a transaction before the method runs and commits it on success or rolls it back on failure.

> **Reference**:
> - JPA persistence-context angle: [3.8 Transactions](<../03-hibernate-and-spring-data-jpa/3.8. Transactions.md>).
> - DB-level ACID: [11.4 Database Transactions and ACID Properties](<11.4. Database Transactions and ACID Properties.md>).

## How @Transactional Works

Spring wraps the annotated method in an AOP proxy that opens a transaction, runs the method, then commits or rolls back based on the outcome.

```
Method call
  │
  ▼
Proxy intercepts → begin transaction (open DB connection)
  │
  ▼
Execute actual method
  │
  ├── Success (no exception) → COMMIT
  │
  └── RuntimeException / Error → ROLLBACK
```

```java
@Service
public class AccountService {

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        accountRepository.debit(fromId, amount);
        accountRepository.credit(toId, amount);
        // If credit throws, the debit is rolled back automatically
    }
}
```

By default only unchecked exceptions (`RuntimeException`, `Error`) trigger rollback. Checked exceptions do not unless you configure it:

```java
@Transactional(rollbackFor = Exception.class)  // rollback on all exceptions
```

## Transaction Propagation

Propagation controls what happens when a `@Transactional` method calls another `@Transactional` method: should they share one transaction or get separate ones?

```java
@Transactional  // outer
public void placeOrder() {
    // save order
    paymentService.processPayment(); // inner: same transaction, or its own?
}
```

### REQUIRED (default)

The inner method joins the outer transaction (or creates its own if none exists). Both succeed or fail together.

```
placeOrder() starts Transaction 1
  → processPayment() joins Transaction 1
  → if processPayment fails, all of Transaction 1 rolls back
```

### REQUIRES_NEW

The inner method gets its own new transaction; the outer is suspended until the inner finishes. The inner can commit or roll back independently. Useful for audit logging, where the log entry should persist even if the main operation fails.

```
placeOrder() starts Transaction 1
  → processPayment() starts Transaction 2 (Transaction 1 suspended)
  → if processPayment fails, only Transaction 2 rolls back; Transaction 1 can commit
```

### MANDATORY

The inner method must run inside an existing transaction and throws if there is none, forcing it to never run standalone.

```
With an outer transaction → joins it
Called directly (no outer) → exception: "No existing transaction found"
```

### All Propagation Types

| Propagation   | No outer TX exists | Outer TX exists                |
| ------------- | ------------------ | ------------------------------ |
| REQUIRED      | Create new         | Join outer                     |
| REQUIRES_NEW  | Create new         | Create new (suspend outer)     |
| MANDATORY     | Exception          | Join outer                     |
| SUPPORTS      | Run without TX     | Join outer                     |
| NOT_SUPPORTED | Run without TX     | Suspend outer, run without TX  |
| NEVER         | Run without TX     | Exception                      |
| NESTED        | Create new         | Create nested (savepoint)      |

> **Note**: REQUIRED covers most cases. Use REQUIRES_NEW when an inner operation must commit independently. The others are rare.

## Setting the Isolation Level

```java
@Transactional(isolation = Isolation.SERIALIZABLE)
public void incrementBalance(Long id, BigDecimal amount) {
    Account account = accountRepository.findById(id).orElseThrow();
    account.setAmount(account.getAmount().add(amount));
    accountRepository.save(account);
}
```

| Value                        | Maps To                                                       |
| ---------------------------- | ------------------------------------------------------------- |
| `Isolation.DEFAULT`          | The database default (Read Committed for PG, Repeatable Read for MySQL) |
| `Isolation.READ_UNCOMMITTED` | Lowest; dirty reads possible                                  |
| `Isolation.READ_COMMITTED`   | No dirty reads                                               |
| `Isolation.REPEATABLE_READ`  | Consistent reads within the transaction                      |
| `Isolation.SERIALIZABLE`     | Highest; transactions behave as if sequential                |

> **Note**: for concurrent updates to the same row (like incrementing a balance), `Isolation.SERIALIZABLE` prevents lost updates, at the cost of conflict retries.

## Testing Concurrent Transactions

Fire many requests simultaneously to verify the isolation level handles concurrent updates:

```bash
# 100 requests, 10 concurrent (curl + xargs)
seq 100 | xargs -P 10 -I {} curl --location --request PUT \
  'http://127.0.0.1:8080/employees/incrementBalance/1'

# 100 requests, 10 concurrent (ApacheBench)
ab -n 100 -c 10 -T 'application/json' -m PUT \
  http://127.0.0.1:8080/employees/incrementBalance/1
```

```
Without proper isolation:  start 1000, 100 × ₹10 → expected 2000, actual 1050 (lost updates)
With Isolation.SERIALIZABLE: start 1000, 100 × ₹10 → 2000 (some transactions retry after conflict)
```

If the final balance does not match, the isolation level is not strong enough for concurrent writes.

## Common @Transactional Attributes

```java
@Transactional(
    isolation = Isolation.READ_COMMITTED,
    propagation = Propagation.REQUIRED,
    rollbackFor = Exception.class,
    readOnly = true,
    timeout = 30
)
```

| Attribute     | Purpose                                              | Default                  |
| ------------- | ---------------------------------------------------- | ------------------------ |
| `isolation`   | Isolation level                                      | `DEFAULT` (DB's default) |
| `propagation` | Transaction propagation                              | `REQUIRED`               |
| `rollbackFor` | Which exceptions trigger rollback                    | `RuntimeException`, `Error` |
| `readOnly`    | Hint to optimize read-only transactions (no write locks) | `false`              |
| `timeout`     | Max seconds before the transaction is rolled back    | Database default         |

> **Note**: `readOnly = true` suits GET operations; it lets the persistence layer skip dirty-checking and the DB optimize since no writes will happen.

## Self-Invocation and Proxy Behavior

Because `@Transactional` uses AOP proxies, calling a `@Transactional` method from within the same class bypasses the proxy, so the transaction does not apply.

```java
@Service
public class OrderService {

    public void placeOrder() {
        this.audit();   // direct call bypasses the proxy; no transaction
    }

    @Transactional
    public void audit() { ... }
}
```

**Fixes**:

- Move `audit()` to a separate bean and inject it, so calls go through the proxy.
- Inject the bean into itself (self-injection) and call `self.audit()` instead of `this.audit()`.
- Enable `@EnableAspectJAutoProxy(exposeProxy = true)` and call `((OrderService) AopContext.currentProxy()).audit()`.

> **Note**: the same applies to private and `final` methods; proxies cannot intercept them.

> **Reference**: proxy mechanics in [10.4 Spring Proxy and Internal Working of AOP](<../10-aspect-oriented-programming/10.4. Spring Proxy and Internal Working of AOP.md>).

## Q&A

1. **How does `@Transactional` actually work?** Spring creates an AOP proxy around the bean. The proxy opens a transaction (via `PlatformTransactionManager`), runs the method, and commits on success or rolls back on a `RuntimeException`/`Error`.
2. **Why no rollback on checked exceptions by default?** Spring inherited EJB's convention: only unchecked exceptions trigger rollback. Override with `@Transactional(rollbackFor = Exception.class)` to include checked exceptions.
3. **Why doesn't `@Transactional` work on self-invocation or private methods?** AOP proxies intercept only external calls through the proxy reference. A `this.method()` call goes directly to the target, skipping the proxy; private methods are not visible to it. Move the method to another bean or inject self via the proxy.
4. **REQUIRED vs REQUIRES_NEW?** REQUIRED joins an existing transaction (or starts one). REQUIRES_NEW always starts a fresh transaction, suspending the outer; useful when an inner operation must commit independently (such as audit logging).
5. **What does `readOnly = true` do?** A hint to skip dirty-checking, optionally route to a read replica, and let the DB optimize. It does not enforce read-only at the SQL level on most databases.
6. **How does `@Transactional` interact with isolation levels?** `@Transactional(isolation = ...)` sets the JDBC isolation for the transaction's connection. Default is `Isolation.DEFAULT`, the DB's own default (see [11.5 Concurrent Transaction Management and Isolation Levels](<11.5. Concurrent Transaction Management and Isolation Levels.md>)).
7. **What is the proxy mode for handling self-invocation?** Use `AopContext.currentProxy()` (with `exposeProxy = true`) or inject the bean into itself; both re-enter through the proxy. Cleaner still: split into separate beans.
