Isolation levels define what a transaction can see (preventing dirty, non-repeatable, and phantom reads), set at the database level and enforced automatically. Locks control access to specific rows (preventing concurrent modification), applied by you at the application or query level.

```
Isolation levels → "What data can other transactions see?"
  → prevents reading inconsistent data; the database handles it

Locks → "Who can modify this row right now?"
  → prevents concurrent writes to the same row; you choose where to apply them
```

The same scenario (incrementing a balance from 1000) plays out three ways:

```
Serializable isolation (no locks):
  T1 reads 1000; T2 reads 1000; T2 writes 1010, commits
  T1 writes 1010 → CONFLICT → exception → T1 aborted
  (correct data, but T1 failed and needs an application-level retry)

Pessimistic lock:
  T1 locks row, reads 1000; T2 tries to read → WAITS
  T1 writes 1010, commits, releases lock
  T2 reads 1010, writes 1020, commits
  (both succeed, no exceptions, no retries)

Optimistic lock:
  T1 reads 1000 (version=1); T2 reads 1000 (version=1)
  T2 writes 1010 (version=2), commits
  T1 writes 1010 → version check fails → exception → retry
  T1 reads 1010 (version=2), writes 1020 (version=3), commits
  (correct data, T1 retried once)
```

| Approach                | How It Handles Conflict                                |
| ----------------------- | ------------------------------------------------------ |
| Serializable isolation  | Detects the conflict, throws, you deal with it          |
| Pessimistic lock        | Prevents the conflict; the other transaction waits      |
| Optimistic lock         | Detects the conflict, throws, retry with fresh data     |

## The Problem

100 concurrent requests increment the same balance:

```bash
seq 100 | xargs -P 10 -I {} curl -X PUT \
  'http://localhost:8080/employees/incrementBalance/1'
```

```
Without locks:  start 1000, 100 × ₹10 → expected 2000, actual 1050 (lost updates)
Exception: "Row was updated or deleted by another transaction" (StaleObjectStateException)
```

Two approaches solve this: optimistic and pessimistic locking.

---

## Optimistic Locking

Assumes conflicts are rare. It locks nothing; instead it uses a version number to detect whether someone else changed the data between read and write.

```
Transaction A                         Transaction B
  Read(balance=1000, version=1)         │
  │                                     Read(balance=1000, version=1)
  balance = 1010                        balance = 1010
  UPDATE WHERE version=1                │
  → success (version now 2)             │
  │                                     UPDATE WHERE version=1
  │                                     → FAIL (version is 2, not 1)
  │                                     → OptimisticLockException → retry
```

**Add `@Version` to the entity**; Hibernate then checks and increments it on every update, with no repository or service changes needed:

```java
@Entity
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private BigDecimal balance;

    @Version
    private Long version;   // Hibernate manages this automatically
}
```

**What Hibernate generates** (if the version already changed, zero rows update and Hibernate throws `OptimisticLockException`):

```sql
UPDATE employees
SET balance = 1010, version = 2
WHERE id = 1 AND version = 1;   -- checks the version hasn't changed
```

**Handling the retry with Spring Retry** (bounded attempts plus exponential backoff):

```java
@Service
public class EmployeeService {

    @Retryable(
        retryFor = OptimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 50, multiplier = 2)
    )
    @Transactional
    public void incrementBalance(Long id, BigDecimal amount) {
        Employee employee = employeeRepository.findById(id).orElseThrow();
        employee.setBalance(employee.getBalance().add(amount));
        employeeRepository.save(employee);
    }

    @Recover
    public void recover(OptimisticLockingFailureException ex, Long id, BigDecimal amount) {
        log.error("Failed to update balance after retries, id={}", id, ex);
        throw new ConcurrencyException("Could not update balance, please retry");
    }
}
```

> **Note**: this requires `spring-retry` and `spring-aspects` on the classpath plus `@EnableRetry` on a `@Configuration` class.

> **Note**: prefer bounded retries with backoff over a naive recursive `catch` block. Self-calling from a catch risks `StackOverflowError` under sustained contention and creates a retry storm that amplifies DB load. `@Retryable` caps the depth via `maxAttempts`, backoff (50ms, 100ms, 200ms) spaces retries so contention can drain, and `@Recover` gives a clean terminal path that surfaces a meaningful exception instead of looping silently.

## Pessimistic Locking

Assumes conflicts are likely. It explicitly locks the row in the database; other transactions wait until the lock is released. No conflicts and no retries, but slower because transactions queue.

```
Transaction A                         Transaction B
  SELECT ... FOR UPDATE (locks row)     │
  Read(balance=1000)                    │
  │                                     SELECT ... FOR UPDATE
  │                                     → WAITING (row locked by A)
  balance = 1010                        │ (still waiting)
  COMMIT (lock released)                │
  │                                     → lock acquired
  │                                     Read(balance=1010), balance=1020, COMMIT
```

**Add `@Lock` on a repository query**:

```java
public interface EmployeeRepository extends JpaRepository<Employee, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT e FROM Employee e WHERE e.id = :id")
    Optional<Employee> findByIdWithLock(@Param("id") Long id);
}
```

**What Hibernate generates**:

```sql
SELECT * FROM employees WHERE id = 1 FOR UPDATE;   -- locks the row
```

**Service** (the row stays locked until this transaction ends):

```java
@Service
public class EmployeeService {

    @Transactional
    public void incrementBalance(Long id, BigDecimal amount) {
        Employee employee = employeeRepository.findByIdWithLock(id).orElseThrow();
        employee.setBalance(employee.getBalance().add(amount));
        employeeRepository.save(employee);
    }
}
```

### Lock Modes

| Mode                | SQL          | What It Does                                      |
| ------------------- | ------------ | ------------------------------------------------- |
| `PESSIMISTIC_READ`  | `FOR SHARE`  | Shared lock; others can read but not write         |
| `PESSIMISTIC_WRITE` | `FOR UPDATE` | Exclusive lock; others can neither read nor write  |

`PESSIMISTIC_WRITE` is the common choice: if you are locking, you usually want exclusive access.

### Lock Timeouts: Avoiding Indefinite Waits

A pessimistic lock without a timeout can wedge a request forever if the holding transaction stalls, so always cap the wait. On timeout you get a `LockTimeoutException`; handle it (retry, fail fast, or surface a 503) rather than letting the request hang.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints({
    @QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000") // 3s, in ms
})
@Query("SELECT e FROM Employee e WHERE e.id = :id")
Optional<Employee> findByIdWithLock(@Param("id") Long id);
```

## Optimistic vs Pessimistic

| Dimension     | Optimistic                        | Pessimistic                     |
| ------------- | --------------------------------- | ------------------------------- |
| Assumption    | Conflicts are rare                | Conflicts are likely            |
| How it works  | Version check on update           | Lock the row on read            |
| DB lock       | No                                | Yes (`FOR UPDATE`)              |
| If conflict   | Fails, needs retry                | Waits for lock release          |
| Performance   | Better (no locking overhead)      | Slower (transactions wait)      |
| Deadlock risk | No                                | Yes                             |
| Best for      | Read-heavy, low contention        | Write-heavy, high contention    |
| Example       | Google Docs (collaborative edits) | Airline seat booking            |

## Transaction Strategies in the Real World

| Strategy             | Use Case                                              | Example                          |
| -------------------- | ----------------------------------------------------- | -------------------------------- |
| Read Committed       | E-commerce; consistent data with good performance      | Amazon                           |
| Read Uncommitted     | Analytics, non-critical reporting                      | Google Analytics                 |
| Serializable         | Financial transactions, critical operations            | Banking, stock trading           |
| Optimistic Locking   | Collaborative editing; rare conflicts needing detection | Google Docs                      |
| Pessimistic Locking  | Resource booking; needs exclusive access               | Airline reservations             |
| No Transactions      | Large-scale distributed systems; eventual consistency   | Social feeds                     |

## Q&A

1. **Optimistic vs pessimistic locking, when to use which?** Optimistic (`@Version`) when conflicts are rare and you do not want to hold DB locks (read-heavy systems, collaborative editing). Pessimistic (`SELECT ... FOR UPDATE`) when conflicts are frequent and you cannot afford retries (booking systems, inventory deductions).
2. **How does `@Version` prevent lost updates?** Hibernate adds `WHERE id = ? AND version = ?` to every UPDATE. If another transaction bumped the version first, zero rows update and Hibernate throws `OptimisticLockException`, signaling the caller to retry with fresh data.
3. **`PESSIMISTIC_READ` vs `PESSIMISTIC_WRITE`?** `PESSIMISTIC_READ` (`FOR SHARE`): others can read but not modify. `PESSIMISTIC_WRITE` (`FOR UPDATE`): exclusive lock; others cannot even read the row in many DBs. `PESSIMISTIC_WRITE` is the common choice.
4. **Why use locks if you already use Serializable isolation?** Serializable detects conflicts and aborts, leaving retry to the caller. Pessimistic locks queue transactions instead (no retries, no exceptions) at the cost of throughput. Optimistic locks shift conflict detection to the application with a smaller DB footprint.
5. **What is the deadlock risk with pessimistic locking?** Two transactions each holding a lock the other needs will deadlock. Most DBs detect and abort one, so your code must handle the abort and retry. Optimistic locking has no deadlock risk.
6. **Where do you put `@Version` and what type should it be?** On a single field of an `@Entity`, typically `Long`, `Integer`, or `Timestamp`. Hibernate manages it; you never set it manually.
