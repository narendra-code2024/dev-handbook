## The Problem: Services Don't Know Each Other

Microservices need to communicate, but they do not know each other's IP and port. With a few services you could hardcode addresses, but that breaks as services scale:

```
3 services → each needs to know 2 others (manageable)

12 services → each needs to know 11 others
  → Add 1 new service → update all 12 existing services
  → IP changes → update everywhere
```

---

## The Solution: Service Registry

A centralized location where every service registers its address (IP plus port). When a service wants to talk to another, it asks the registry instead of hardcoding the address.

```
Without registry:

  Service A ↔ Service B     Every service must know
  Service A ↔ Service C     every other service's address.
  Service B ↔ Service C     Add one service → update all others.


With registry:

  Service A ──register──→ ┌───────────────────┐
                          │                   │
  Service B ──register──→ │  Service Registry │
                          │  (knows everyone) │
  Service C ──register──→ └───────────────────┘

  Service A wants to call B?
    → asks registry: "Where is Service B?"
    → registry returns: 10.4.5.6:7777
    → Service A calls B directly at that address
```

---

## What is Eureka?

A REST-based service registry developed by Netflix and integrated with Spring Cloud. A microservices system using Eureka has two kinds of app:

- **Eureka Server (the registry)**: a standalone Spring Boot app whose only job is to track all other services. You create one `discovery-service` for this.
- **Eureka Client (every other service)**: your actual microservices (order-service, inventory-service). They register themselves with the server on startup so others can find them.

```
┌───────────────────┐                  ┌─────────────────────────┐
│ Order Service     │                  │ Discovery Service       │
│ (Eureka Client)   │──register──→     │ (Eureka Server)         │
│ 10.1.2.3:8081     │                  │ port: 8761              │
└───────────────────┘                  │                         │
                                       │ Knows:                  │
┌───────────────────┐                  │  order-service →        │
│ Inventory Service │──register──→     │    10.1.2.3:8081        │
│ (Eureka Client)   │                  │  inventory-service →    │
│ 10.4.5.6:8082     │                  │    10.4.5.6:8082        │
└───────────────────┘                  └─────────────────────────┘
```

> **Note**: Eureka is one option. Consul (HashiCorp) and Kubernetes-native discovery (DNS via `Service` objects) are common alternatives; prefer k8s discovery if you are already on Kubernetes, since it removes a moving part.

---

## How Eureka Works

```
Order Service starts up
       │
       ▼
Registers with Eureka Server:
  "I'm order-service, my address is 10.1.2.3:8081"
       │
       ▼
Sends heartbeats to Eureka Server every 30s:
  "I'm still alive"
       │
       ▼
Inventory Service wants to call Order Service:
  → asks Eureka Server: "Where is order-service?"
  → Eureka returns: 10.1.2.3:8081
  → Inventory Service calls that address directly
       │
       ▼
If Order Service stops sending heartbeats for 90s:
  → Eureka removes it from the registry
  → Other services can no longer discover it
```

## Setting Up the Eureka Server

Create a `discovery-service` from [start.spring.io](https://start.spring.io/) (Group `com.example.ecommerce`, dependency Eureka Server / `spring-cloud-starter-netflix-eureka-server`), then enable it and configure it.

**Enable the server**:

```java
@SpringBootApplication
@EnableEurekaServer
public class DiscoveryServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(DiscoveryServiceApplication.class, args);
    }
}
```

**Configure it**:

```yaml
spring:
  application:
    name: eureka-server

server:
  port: 8761

eureka:
  client:
    register-with-eureka: false   # the server is not a client of itself
    fetch-registry: false         # nothing to fetch from itself
```

| Property                       | Why                                                       |
| ------------------------------ | --------------------------------------------------------- |
| `server.port: 8761`            | Default Eureka port (standard across Spring Boot projects) |
| `register-with-eureka: false`  | The server itself should not register as a client          |
| `fetch-registry: false`        | The server does not need to fetch the registry from itself |

> **Note**: visit `http://localhost:8761` for the Eureka dashboard showing all registered services.

## Setting Up the Eureka Clients

Add the following to every microservice (order-service, inventory-service, from [12.2 Setting Up the Order and Inventory Services](<12.2. Setting Up the Order and Inventory Services.md>)).

**Add the client dependency and Spring Cloud BOM** (the BOM only if not already present):

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
</dependency>
```

```xml
<properties>
    <spring-cloud.version>2023.0.3</spring-cloud.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

**Configure the client**:

```yaml
# order-service
spring:
  application:
    name: order-service

eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka
```

> **Note**: `spring.application.name` is the name registered in Eureka and the name other services use to discover this one. `defaultZone` points to the Eureka Server; `http://localhost:8761/eureka` is also the default, so it works even if left unset.

## Calling Another Service via Discovery

Once registered, services discover each other by name instead of hardcoded IP and port. The endpoint being called lives in Order Service; Inventory Service resolves it through `DiscoveryClient`.

```java
// Order Service: the endpoint being called
@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    @GetMapping("/helloOrders")
    public String helloOrders() {
        return "Hello from order service";
    }
}
```

```java
// Inventory Service: calling Order Service via discovery
@RestController
@RequestMapping("/api/v1/products")
@RequiredArgsConstructor
public class ProductController {

    private final DiscoveryClient discoveryClient;
    private final RestClient restClient;

    @GetMapping("/fetchOrders")
    public String fetchFromOrderService() {
        // 1. Ask Eureka where order-service lives
        ServiceInstance orderService = discoveryClient
            .getInstances("order-service")
            .getFirst();

        // 2. Resolve its URI (IP:port)
        URI uri = orderService.getUri();

        // 3. Call it at the discovered address
        return restClient.get()
            .uri(uri + "/api/v1/orders/helloOrders")
            .retrieve()
            .body(String.class);
    }
}
```

```
Inventory Service: discoveryClient.getInstances("order-service")
       │
       ▼
Eureka returns: order-service is at http://10.1.2.3:8081
       │
       ▼
Inventory Service calls: http://10.1.2.3:8081/api/v1/orders/helloOrders
       │
       ▼
Gets response: "Hello from order service"
```

> **Note**: no hardcoded URLs. If order-service moves to a different port or host, Eureka resolves the new address automatically.

## Eureka Client Configuration Options

```yaml
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka
    register-with-eureka: true    # register this service (default: true)
    fetch-registry: true          # fetch the list of other services (default: true)
  instance:
    prefer-ip-address: true       # register IP instead of hostname
    lease-renewal-interval-in-seconds: 30      # heartbeat interval (default: 30s)
    lease-expiration-duration-in-seconds: 90   # evicted if silent this long (default: 90s)
```

## Production Considerations

- **High availability**: run multiple Eureka Server instances peer-replicating to each other (point each peer's `defaultZone` at the others). A single node is a hidden SPOF; if it dies, no new client can discover anything.
- **Heartbeat / TTL trade-off**: the 30s renew and 90s eviction defaults mean a hard-crashed instance (no graceful deregister) keeps receiving traffic for up to 90s. Lowering both speeds up failure detection but adds chatter and risks false eviction during long GC pauses. Tune only after measuring the pain.
- **Self-preservation mode**: Eureka stops evicting instances when too many heartbeats are missed in a short window, to avoid network-partition false positives. Understand it before disabling.
- **Prefer DNS / k8s-native discovery on Kubernetes**: k8s `Service` objects already do discovery via DNS. Adding Eureka on top duplicates the registry. Use Eureka mostly outside k8s or in hybrid setups.
- **Secure the registry**: Eureka has no auth by default. In production put it behind mTLS / Spring Security on a private network; anyone who can reach it can register fake services or scrape your topology.
- **Pair with client-side load balancing**: Spring Cloud LoadBalancer consumes the Eureka registry to round-robin across instances, with no extra config once both are on the classpath.

## Q&A

1. **What is service discovery and why is it needed?** A mechanism where services register their address with a central registry and callers look up the address by service name. It removes hardcoded IP and port, which break as services scale, restart, or move hosts.
2. **What is the difference between a Eureka Server and a Eureka Client?** The server is the registry itself (one standalone app, port 8761 by default). Clients are the actual microservices; they register on startup and can query the registry to discover others.
3. **How does Eureka detect a dead service?** Clients send heartbeats every 30s. If the server hears nothing for 90s (default `lease-expiration-duration`), it evicts that instance from the registry.
4. **Why set `register-with-eureka: false` on the server itself?** It is the registry, not a consumer, so it should not register as a client of itself. The same logic applies to `fetch-registry: false`.
5. **Client-side vs server-side discovery?** Server-side discovery hides the registry behind a load balancer (the client just hits the LB). Client-side (Eureka plus Spring Cloud LoadBalancer) puts the lookup in the caller, which picks an instance itself. Eureka is client-side.
6. **Is Eureka a single point of failure?** A single node is. Production runs a peer-replicated cluster where each server is also a client of the others, so one node failing does not break discovery.
