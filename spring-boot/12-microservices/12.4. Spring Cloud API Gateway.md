An API Gateway is the single entry point for all clients (web, mobile, etc.), routing each request to the correct microservice behind the scenes.

Without a gateway, clients must know the IP and port of every microservice, and those change as services scale or restart:

```
Without API Gateway:

  Client ──→ Order Service (10.1.2.3:8081)
  Client ──→ Inventory Service (10.4.5.6:8082)
  Client ──→ Payment Service (10.7.8.9:8083)
  (client must know every address)


With API Gateway:

  Client ──→ API Gateway (single address, port 8080)
                  │
                  ├──→ Order Service
                  ├──→ Inventory Service
                  └──→ Payment Service
  (client knows only one address)
```

> **Note**: Spring Cloud Gateway is the modern choice. The older Zuul (Zuul 1, Netflix) is in maintenance mode; do not start a new project with it.

## Three Building Blocks

```
Request arrives at API Gateway
       │
       ▼
┌─────────────────────────────┐
│  Route (where to send)      │
│    │                        │
│    ├── Predicate (if match) │
│    │                        │
│    └── Filters (modify)     │
└─────────────────────────────┘
       │
       ▼
Downstream Microservice
```

| Block     | What It Does                                        | Example                            |
| --------- | --------------------------------------------------- | ---------------------------------- |
| Route     | The destination service to send the request to      | Order Service, Inventory Service   |
| Predicate | The condition; only route if this matches            | Path matches `/orders/**`, GET     |
| Filter    | Modify request/response before or after routing      | Add header, strip prefix, redirect |

## Setup

Create an `api-gateway` from [start.spring.io](https://start.spring.io/) with dependencies Gateway (`spring-cloud-starter-gateway`) and Eureka Discovery Client, then configure its routes.

```yaml
spring:
  application:
    name: api-gateway
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://ORDER-SERVICE
          predicates:
            - Path=/api/v1/orders/**
          filters:
            - StripPrefix=2

        - id: inventory-service
          uri: lb://INVENTORY-SERVICE
          predicates:
            - Path=/api/v1/inventory/**
          filters:
            - StripPrefix=2

server:
  port: 8080

eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka
```

> **Note**:
> - If Spring Initializr adds `spring-cloud-starter-gateway-mvc`, remove the `-mvc`; the gateway uses reactive Netty, not MVC.
> - The gateway is also a Eureka Client: it discovers where each service lives, so there are no hardcoded service addresses.

## Understanding the Config

### Route

```yaml
- id: order-service              # unique name for this route
  uri: lb://ORDER-SERVICE        # destination service
```

`lb://ORDER-SERVICE` means use the load balancer (`lb://`) to resolve `ORDER-SERVICE`, the `spring.application.name` registered in Eureka. The gateway asks Eureka for the address and routes there, spreading traffic if there are multiple instances.

### Predicate

```yaml
predicates:
  - Path=/api/v1/orders/**       # route only if the URL matches this pattern
```

| Predicate                        | What It Matches                |
| -------------------------------- | ------------------------------ |
| `Path=/api/v1/orders/**`         | URL path matches the pattern   |
| `Method=GET`                     | Only GET requests              |
| `Method=GET,POST`                | Only GET or POST requests      |
| `Header=User-Agent, Mozilla/*`   | Request has this header value  |

### Filter

```yaml
filters:
  - StripPrefix=2                # remove the first 2 path segments
```

`StripPrefix` removes leading path segments before forwarding. The `/api/v1` prefix is for the gateway's routing; the downstream service never sees it:

```
Client sends:     /api/v1/orders/core/helloOrders
StripPrefix=2:    removes /api/v1
Service receives: /orders/core/helloOrders
```

---

## Common Built-in Filters

| Filter                          | What It Does                                  | Example                                  |
| ------------------------------- | --------------------------------------------- | ---------------------------------------- |
| `StripPrefix=N`                 | Remove the first N path segments               | `StripPrefix=2` removes `/api/v1`        |
| `AddRequestHeader=Key, Value`   | Add a header to the request sent to the service | `AddRequestHeader=X-Custom-Header, Anuj` |
| `AddResponseHeader=Key, Value`  | Add a header to the response sent to the client | `AddResponseHeader=X-Response-Id, abcd`  |
| `RemoveRequestHeader=Name`      | Remove a header from the request               | `RemoveRequestHeader=Cookie`             |
| `RedirectTo=status, URL`        | Redirect the request to another URL            | `RedirectTo=302, https://example.com`    |

`AddRequestHeader` is the common one in practice: pass a user ID or verified token from the gateway down to the service after authentication.

```yaml
- id: inventory-service
  uri: lb://INVENTORY-SERVICE
  predicates:
    - Path=/api/v1/inventory/**
  filters:
    - StripPrefix=2
    - AddRequestHeader=X-Custom-Header, Anuj
```

The downstream service reads it from the request:

```java
@GetMapping("/fetchOrders")
public String fetchOrders(HttpServletRequest request) {
    String customHeader = request.getHeader("X-Custom-Header"); // "Anuj"
    // ...
}
```

## How a Request Flows Through the Gateway

```
Client: GET http://localhost:8080/api/v1/orders/core/helloOrders
       │
       ▼
API Gateway (port 8080)
       │
       ▼
Check predicates: Path=/api/v1/orders/** → matches order-service route
       │
       ▼
Apply filters: StripPrefix=2 → /api/v1 removed → /orders/core/helloOrders
       │
       ▼
Resolve URI: lb://ORDER-SERVICE → ask Eureka → 10.1.2.3:8081
       │
       ▼
Forward to: http://10.1.2.3:8081/orders/core/helloOrders
       │
       ▼
Order Service responds → Gateway returns the response to the client
```

> **Note**: start services in order: Discovery Service first, then the Eureka Clients (Order, Inventory) so they register, then the gateway. If the gateway starts before services register you may see "No server available"; wait around 30s for Eureka to sync.

## Context-Path Is Optional

Some projects set `server.servlet.context-path: /orders` on a service so every endpoint gets that prefix automatically (`@RequestMapping("/core")` becomes `/orders/core/...`). This is not mandatory: putting `/orders` directly in `@RequestMapping` works the same. The gateway routes on the predicate pattern, not the context-path.

```
With context-path:    context-path=/orders + @RequestMapping("/core")
Without context-path:  @RequestMapping("/orders/core")
→ Both produce: /orders/core/...
```

## Production Considerations

- **Auth at the gateway**: validate JWT / OAuth2 tokens once at the gateway and forward the verified identity to downstream services in a header. Avoids every service repeating auth logic.
- **Rate limiting**: the built-in `RequestRateLimiter` filter (token-bucket via Redis) applies per-route or per-user to protect downstreams from spikes.
- **Circuit-breaker filter**: wrap routes with the `CircuitBreaker` filter so a failing downstream returns a fallback instead of long timeouts (see [12.6 Resilience4J](<12.6. Circuit Breaker, Retry and Rate Limiter with Resilience4J.md>)).
- **Run multiple gateway replicas**: the gateway is the single entry point, so it is also the single point of failure. Always run 2+ replicas behind an external load balancer (cloud LB, k8s `Service` of type `LoadBalancer`).
- **TLS termination**: terminate TLS at the gateway or one hop in front (cloud LB / ingress). Internal hops use mTLS or a private network.
- **Observability**: enable access logging, metrics (Micrometer plus Prometheus), and propagate tracing headers (B3 / W3C Trace Context). The gateway is the natural place to inject correlation IDs.
- **No business logic here**: the gateway is for routing, auth, rate limiting, observability, and traffic shaping. Anything domain-specific belongs in the services.

> **Note**: Spring Cloud Gateway is reactive (Netty). Do not add servlet/blocking dependencies to the same module; they conflict and cause startup or runtime issues. Keep the gateway lean.

## Q&A

1. **Why put an API Gateway in front of microservices?** So clients need a single address instead of every service's. It also centralizes cross-cutting concerns: auth, rate limiting, logging, CORS, and request/response transformation.
2. **What are Routes, Predicates, and Filters?** Route is the destination service. Predicate is the condition that must match (path, method, header). Filter transforms the request before forwarding (`StripPrefix`) or the response after (`AddResponseHeader`).
3. **What does `lb://ORDER-SERVICE` mean?** `lb://` tells the gateway to use Spring Cloud LoadBalancer to resolve the target. `ORDER-SERVICE` is the `spring.application.name` in Eureka; the gateway looks up instances and balances across them.
4. **Why is Spring Cloud Gateway reactive (Netty), not Servlet?** It handles many in-flight requests concurrently with low resource use. An MVC variant exists, but the reactive Netty stack is the standard choice for a gateway under load.
5. **API Gateway vs OpenFeign load balancing?** The gateway balances client-to-service traffic (north-south). OpenFeign plus Spring Cloud LoadBalancer balances service-to-service traffic (east-west). Both use Eureka underneath.
6. **Why not put business logic in the gateway?** It is the entry point for the whole system; keeping it focused on routing, auth, and rate limiting keeps deploys safe and the gateway fast. Domain logic there turns it into a distributed monolith.
