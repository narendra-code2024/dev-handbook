Resilience4J is a lightweight library for making microservices resilient to failures. Instead of writing retry, rate limiting, or circuit breaking from scratch, you add annotations and config.

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>
```

> **Note**: Resilience4J replaced Hystrix, which is no longer maintained. Do not reach for Hystrix in new code.

---

## Three Key Patterns

| Pattern         | Purpose                                          | When to Use                                       |
| --------------- | ------------------------------------------------ | ------------------------------------------------- |
| Retry           | Try again if a call fails                          | Temporary failures (network blip, restart)        |
| Rate Limiter    | Cap how many calls run in a time window            | Protect downstream services, throttle abuse       |
| Circuit Breaker | Stop calling a service that is down                | Prolonged failures, prevent cascade               |

---

## Retry

If a service call fails, try again a configured number of times before giving up and invoking the fallback.

```java
@Retry(name = "inventoryRetry", fallbackMethod = "createOrderFallback")
@Transactional
public OrderResponseDto createOrder(OrderRequestDto orderRequest) {
    log.info("Calling the create order method");
    Double totalPrice = inventoryFeignClient.reduceStocks(orderRequest);
    // ... create and save order
}

// Fallback, called after all retries fail.
// Must match the original return type and params, plus a Throwable.
public OrderResponseDto createOrderFallback(OrderRequestDto orderRequest, Throwable throwable) {
    log.error("Fallback occurred due to: {}", throwable.getMessage());
    return new OrderResponseDto();
}
```

```
Call fails → wait → retry 1 → wait → retry 2 → wait → retry 3 → all failed → fallback
```

```yaml
resilience4j:
  retry:
    instances:
      inventoryRetry:
        maxAttempts: 3
        waitDuration: 500ms
```

| Property      | What It Does                  | Production Value |
| ------------- | ----------------------------- | ---------------- |
| `maxAttempts` | Total attempts including first | 3-5              |
| `waitDuration`| Wait time between retries      | 100-500ms        |

> **Note**:
> - Only retry idempotent operations. `GET`, `PUT`, `DELETE` are safe. Retrying a `POST` (create-order) can charge the user twice; require an `Idempotency-Key` on the downstream so it can dedupe, or skip retry on `POST`.
> - Use exponential backoff in production (`enableExponentialBackoff: true`, `exponentialBackoffMultiplier: 2`) so retry storms do not pile on a recovering service.

## Rate Limiter

Limit how many calls a method accepts within a time window. Excess calls go to the fallback.

```java
@RateLimiter(name = "inventoryRateLimiter", fallbackMethod = "createOrderFallback")
@Transactional
public OrderResponseDto createOrder(OrderRequestDto orderRequest) {
    // ...
}
```

```
Window: 1 second, limit: 100 calls
  Call 1-100   → method executes normally
  Call 101+    → fallback ("rate limiter does not permit further calls")
  Next window  → counter resets, 100 calls allowed again
```

```yaml
resilience4j:
  rateLimiter:
    instances:
      inventoryRateLimiter:
        limitForPeriod: 100          # max calls in one window
        limitRefreshPeriod: 1s       # window duration
        timeoutDuration: 100ms       # wait for permission before failing
```

| Property             | What It Does                                | Production Value             |
| -------------------- | ------------------------------------------- | ---------------------------- |
| `limitForPeriod`     | Max calls allowed per window                 | 10-1000 (depends on capacity) |
| `limitRefreshPeriod` | How often the limit resets                   | 1s                           |
| `timeoutDuration`    | Wait for permission before going to fallback | 100-500ms                    |

## Circuit Breaker

If a service is consistently failing, stop calling it entirely. This prevents wasting resources on a dead service and avoids cascade failures. It is the opposite of retry: retry says "try again", the circuit breaker says "stop trying."

### Three States

```
CLOSED ──────────────────→ OPEN
(normal, calls go through)    (failures hit threshold)
  ▲                              │
  │                              │ wait duration (e.g., 20s)
  │                              ▼
  └─── success ──── HALF OPEN ───┘
                   (allow few test calls)
                       │
                       └── still failing → back to OPEN
```

- **Closed**: everything works normally. Calls go through; failures are counted.
- **Open**: too many failures (threshold crossed). All calls go straight to the fallback; none reach the method, saving resources.
- **Half Open**: after a wait period, a few test calls are allowed. Success returns to Closed; failure returns to Open.

```java
@CircuitBreaker(name = "inventoryCircuitBreaker", fallbackMethod = "createOrderFallback")
@Transactional
public OrderResponseDto createOrder(OrderRequestDto orderRequest) {
    // ...
}
```

```yaml
resilience4j:
  circuitbreaker:
    instances:
      inventoryCircuitBreaker:
        registerHealthIndicator: true
        slidingWindowSize: 10
        slidingWindowType: COUNT_BASED
        minimumNumberOfCalls: 10
        failureRateThreshold: 50
        waitDurationInOpenState: 10000    # 10 seconds in ms
        permittedNumberOfCallsInHalfOpenState: 3
        automaticTransitionFromOpenToHalfOpenEnabled: true
```

| Property                                       | What It Does                                          |
| ---------------------------------------------- | ----------------------------------------------------- |
| `registerHealthIndicator`                      | Exposes breaker state in the actuator health endpoint  |
| `slidingWindowSize`                            | Number of recent calls to track                        |
| `minimumNumberOfCalls`                         | Min calls before the failure rate is calculated        |
| `failureRateThreshold`                         | Failure percentage that trips the breaker open (e.g. 50) |
| `waitDurationInOpenState`                      | How long to stay open before moving to half-open       |
| `permittedNumberOfCallsInHalfOpenState`        | Test calls allowed in half-open                        |
| `automaticTransitionFromOpenToHalfOpenEnabled` | Auto-transition after the wait duration                |

### Example Walkthrough

```
10 calls made, 6 fail (60% > 50% threshold)
       │
       ▼
State: CLOSED → OPEN (all calls go to fallback)
       │
       ▼
Wait 10 seconds
       │
       ▼
State: OPEN → HALF OPEN (allow 3 test calls)
       │
       ├── 3 calls succeed → HALF OPEN → CLOSED (back to normal)
       └── 2+ calls fail   → HALF OPEN → OPEN (still broken, wait again)
```

## Retry vs Circuit Breaker

| Dimension         | Retry                          | Circuit Breaker                       |
| ----------------- | ------------------------------ | ------------------------------------- |
| Philosophy        | "Try again, it might work"     | "Stop trying, it is broken"           |
| When              | Temporary/intermittent failures | Prolonged/consistent failures         |
| Action on failure | Retry N times                  | Stop all calls, go to fallback        |
| Protects          | The current request            | The system (prevent cascade and waste) |

### Combining Retry and Circuit Breaker

They work together, but the order matters. Resilience4J's recommended composition is `Retry(CircuitBreaker(call))`: retry is the outer layer, the circuit breaker the inner layer. So each retry attempt passes through the breaker, and if the circuit is OPEN, retries fail fast against it (no actual remote calls), avoiding retry storms against a known-failing downstream.

With Spring Boot annotations, declare both on the method and Resilience4J applies the correct order automatically:

```java
@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallback")
@Retry(name = "inventoryService")
public Product getProduct(Long id) { ... }
```

> **Note**: keep `retry.maxAttempts` modest (3-5) and tune the breaker's `slidingWindowSize` and `failureRateThreshold` so the breaker opens before retries amplify load.

## Fallback Method Rules

The fallback method must have the same return type as the original, the same parameters, plus a `Throwable` parameter at the end, and must live on the same bean.

```java
// Original
public OrderResponseDto createOrder(OrderRequestDto orderRequest) { }

// Fallback: same signature plus Throwable
public OrderResponseDto createOrderFallback(OrderRequestDto orderRequest, Throwable throwable) { }
```

## Shared Default Config

Define a `default` config and inherit it per instance with `baseConfig`, overriding only what differs:

```yaml
resilience4j:
  retry:
    configs:
      default:
        maxAttempts: 3
        waitDuration: 500ms
    instances:
      inventoryRetry:
        baseConfig: default
        waitDuration: 200ms    # override just this property
```

## Monitoring with Actuator

Expose breaker state through actuator to watch transitions in real time:

```yaml
management:
  health:
    circuitbreakers:
      enabled: true
  endpoints:
    web:
      exposure:
        include: health,circuitbreakers,retries,ratelimiters
  endpoint:
    health:
      show-details: always
```

```
GET /actuator/circuitbreakers

{
  "inventoryCircuitBreaker": {
    "state": "CLOSED",
    "failureRate": -1,
    "bufferedCalls": 5,
    "failedCalls": 0
  }
}
```

> **Note**: watch the transitions CLOSED → OPEN → HALF_OPEN → CLOSED for production debugging. Pair with distributed tracing (correlation IDs flowing through Feign headers), covered in 13.5.

## Q&A

1. **What problem does the Circuit Breaker pattern solve?** Cascading failure. If a downstream is down, every caller blocks on timeouts and exhausts threads and connections. The breaker opens after a failure threshold, short-circuits to the fallback immediately, and protects upstream resources.
2. **Difference between Retry and Circuit Breaker?** Retry assumes a transient failure and tries again N times. The breaker assumes a sustained failure and stops calling. They combine as `Retry(CircuitBreaker(call))` so retries fail fast against an open breaker instead of hammering a known-failing downstream.
3. **What are the three Circuit Breaker states?** Closed (calls pass, failures counted), Open (calls short-circuit to fallback, no traffic reaches the dependency), Half-Open (a few probe calls; success returns to Closed, failure to Open).
4. **How is the failure rate calculated?** Over a sliding window (count- or time-based) of recent calls. Once `minimumNumberOfCalls` is reached, if `failureRateThreshold` is exceeded, the breaker opens.
5. **What are the rules for a fallback method?** Same name as the configured `fallbackMethod`, same return type, same parameters, plus a `Throwable` (or specific exception type) appended last, on the same bean.
6. **Where does `@Retry` / `@CircuitBreaker` take effect?** Spring AOP wraps the bean in a proxy, so the annotations only fire on external calls into the bean. Self-invocation (calling from within the same class) bypasses the proxy and the annotations do not trigger.

## Quick Revision Cheat Sheet

| Concept           | Remember                                                          |
| ----------------- | ----------------------------------------------------------------- |
| Retry             | "Try again" for transient failures; idempotent ops only            |
| Rate Limiter      | Cap calls per window; protects downstream from spikes              |
| Circuit Breaker   | "Stop trying" for sustained failures; prevents cascade             |
| States            | CLOSED (normal) → OPEN (short-circuit) → HALF_OPEN (probe)         |
| Composition order | `Retry(CircuitBreaker(call))`; retries fail fast against open breaker |
| Fallback signature| Same return type, same params, plus `Throwable` last               |
| Backoff           | Use exponential backoff in production to avoid retry storms        |
| Proxy behavior    | AOP-based; does not fire on self-invocation (like `@Transactional`) |
| Monitoring        | Actuator exposes `/actuator/circuitbreakers`, `/retries`, `/ratelimiters` |
