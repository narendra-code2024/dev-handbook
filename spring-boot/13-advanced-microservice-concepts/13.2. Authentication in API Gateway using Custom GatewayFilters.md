Without gateway authentication, every microservice needs its own Spring Security setup, duplicated across all services. Authenticating once at the gateway removes that duplication: the gateway validates the JWT and passes the user info (userId, roles) downstream as headers, and services trust the gateway.

```
Without gateway auth:
  Order Service     → Spring Security + JWT validation
  Inventory Service → Spring Security + JWT validation
  Payment Service   → Spring Security + JWT validation
  (same code repeated everywhere)

With gateway auth:
  API Gateway → validates JWT once
    │
    ├──→ Order Service     (trusts gateway, no auth code needed)
    ├──→ Inventory Service (trusts gateway, no auth code needed)
    └──→ Payment Service   (trusts gateway, no auth code needed)
```

> **Reference**: builds on the gateway and routes from [12.4 Spring Cloud API Gateway](<../12-microservices/12.4. Spring Cloud API Gateway.md>) and the filter patterns from [13.1 Introduction to API Gateway Filters](<13.1. Introduction to API Gateway Filters.md>).

## How It Works

```
Client sends: GET /api/v1/orders/core/helloOrders
              Authorization: Bearer eyJ...
       │
       ▼
API Gateway, Authentication Filter
       │
       ├── No Authorization header? → 401 Unauthorized (stop here)
       │
       ├── Invalid/expired token? → 401 Unauthorized (stop here)
       │
       └── Valid token?
             │
             ▼
           Extract userId from token
             │
             ▼
           Add X-User-Id header to request (mutate)
             │
             ▼
           Forward to Order Service
             │
             ▼
Order Service reads X-User-Id from the header, knows who the user is
```

```xml
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-jackson</artifactId>
    <version>0.12.6</version>
    <scope>runtime</scope>
</dependency>
```

**JWT service (in API Gateway)**: parses and verifies the token, returning the userId from its subject claim. The secret key must be the same across the user service (which signs tokens) and the gateway (which verifies them).

```java
@Service
public class JwtService {

    @Value("${jwt.secretKey}")
    private String secretKey;

    public Long getUserIdFromToken(String token) {
        Claims claims = Jwts.parser()
            .verifyWith(getSigningKey())
            .build()
            .parseSignedClaims(token)
            .getPayload();

        return Long.valueOf(claims.getSubject());
    }

    private SecretKey getSigningKey() {
        return Keys.hmacShaKeyFor(secretKey.getBytes());
    }
}
```

```properties
# API Gateway application.properties
jwt.secretKey=your-256-bit-secret-key-must-match-user-service
```

### Authentication Filter

Naming the factory with the `GatewayFilterFactory` suffix lets Spring derive the YAML name automatically: `AuthenticationGatewayFilterFactory` becomes just `Authentication` in config.

```java
@Component
@Slf4j
public class AuthenticationGatewayFilterFactory extends
        AbstractGatewayFilterFactory<AuthenticationGatewayFilterFactory.Config> {

    private final JwtService jwtService;

    public AuthenticationGatewayFilterFactory(JwtService jwtService) {
        super(Config.class);
        this.jwtService = jwtService;
    }

    @Override
    public GatewayFilter apply(Config config) {
        return (exchange, chain) -> {

            // Skip auth if disabled via config
            if (!config.isEnabled()) {
                return chain.filter(exchange);
            }

            String authHeader = exchange.getRequest().getHeaders().getFirst("Authorization");

            // No bearer token → 401
            if (authHeader == null || !authHeader.startsWith("Bearer ")) {
                exchange.getResponse().setStatusCode(HttpStatusCode.valueOf(401));
                return exchange.getResponse().setComplete();
            }

            String token = authHeader.split("Bearer ")[1];

            try {
                Long userId = jwtService.getUserIdFromToken(token);

                // Inject userId as a header for downstream services
                exchange.getRequest().mutate()
                    .header("X-User-Id", userId.toString())
                    .build();

                return chain.filter(exchange);

            } catch (Exception e) {
                log.error("Token validation failed: {}", e.getMessage());
                exchange.getResponse().setStatusCode(HttpStatusCode.valueOf(401));
                return exchange.getResponse().setComplete();
            }
        };
    }

    @Data
    public static class Config {
        private boolean enabled = true;
    }
}
```

> **Note**: do not name the boolean field `isEnabled`. Lombok's `@Data` generates `isEnabled()` for a field named `enabled`; naming the field itself `isEnabled` breaks Spring's binding from YAML `args`.

## Route Configuration

Apply the filter per route and toggle it with `args.enabled`:

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://ORDER-SERVICE
          predicates:
            - Path=/api/v1/orders/**
          filters:
            - StripPrefix=2
            - name: Authentication
              args:
                enabled: true       # auth required

        - id: inventory-service
          uri: lb://INVENTORY-SERVICE
          predicates:
            - Path=/api/v1/inventory/**
          filters:
            - StripPrefix=2
            - name: Authentication
              args:
                enabled: false      # public route, no auth
```

## Login Goes Through the Gateway Too

The client always goes through the gateway, including login. The login and register routes simply have authentication disabled, since the user does not have a token yet.

```
Client knows only one URL: http://api-gateway:8080

Login/Register:
  Client → API Gateway → User Service (auth disabled)
                            → validates credentials
                            → returns JWT token

All other calls:
  Client → API Gateway (auth filter validates JWT)
              → forwards to Order/Inventory/etc.
```

The same service can have multiple routes with different predicates and auth settings, because the gateway routes by path, not by service:

```yaml
routes:
  # Public: login, register (no auth)
  - id: user-service-auth
    uri: lb://USER-SERVICE
    predicates:
      - Path=/api/v1/auth/**
    filters:
      - StripPrefix=2
      - name: Authentication
        args:
          enabled: false

  # Protected: user profile, settings (auth required)
  - id: user-service
    uri: lb://USER-SERVICE
    predicates:
      - Path=/api/v1/users/**
    filters:
      - StripPrefix=2
      - name: Authentication
        args:
          enabled: true

  # Protected: orders (auth required)
  - id: order-service
    uri: lb://ORDER-SERVICE
    predicates:
      - Path=/api/v1/orders/**
    filters:
      - StripPrefix=2
      - name: Authentication
        args:
          enabled: true
```

```
/api/v1/auth/login      → User Service (no auth)
/api/v1/auth/register   → User Service (no auth)
/api/v1/users/profile   → User Service (auth required)
/api/v1/users/settings  → User Service (auth required)
/api/v1/orders/**       → Order Service (auth required)
```

## Reading User Info in Downstream Services

The gateway adds `X-User-Id` to the request headers; downstream services just read it and trust that the gateway already validated the token:

```java
@GetMapping("/core/helloOrders")
public String helloOrders(@RequestHeader("X-User-Id") Long userId) {
    return "Hello from order service, userId: " + userId;
}
```

> **Note**: this model assumes downstream services are only reachable via the gateway (internal-only ports, network policies). If a service is also exposed directly, or you need zero-trust between services, each service must still validate the JWT (or a signed gateway-issued header) itself. Also strip any client-supplied `X-User-Id` at the gateway so callers cannot spoof identity by setting the header upstream of the auth filter.

## Authorization (Extending This)

Authentication verifies who the user is; authorization checks what they can do. Add a second filter that extracts roles from the JWT claims, compares them with the route's allowed roles, and returns 403 Forbidden on a mismatch:

```yaml
filters:
  - name: Authentication
    args:
      enabled: true
  - name: Authorization
    args:
      roles: ADMIN, SUPER_ADMIN
```

## Mutating Requests and Responses

**Mutate the request (pre phase)**:

```java
// Add headers
exchange.getRequest().mutate()
    .header("X-User-Id", userId.toString())
    .header("X-User-Role", role)
    .build();

// Change path
exchange.getRequest().mutate()
    .path("/new-path")
    .build();
```

**Mutate the response (post phase)**:

```java
return chain.filter(exchange)
    .then(Mono.fromRunnable(() -> {
        exchange.getResponse().getHeaders()
            .add("X-Response-Time", Instant.now().toString());
    }));
```

## Q&A

1. **Why authenticate at the gateway instead of each microservice?** Centralizing JWT validation avoids duplicating Spring Security in every service. Downstream services trust the gateway and just read `X-User-Id` from a header.
2. **How does the gateway pass identity downstream?** The filter mutates the request and injects headers like `X-User-Id` (and optionally roles) before forwarding. Downstream controllers read them via `@RequestHeader`.
3. **How is the same filter enabled per route?** Via `AbstractGatewayFilterFactory<Config>` with a `Config` class exposing flags. Routes declare `args: { enabled: true/false }`, so login/register opt out while protected routes opt in.
4. **Authentication vs authorization at the gateway?** Authentication proves who the user is (valid token, extract userId). Authorization checks what they can do (role claims vs the route's required roles), usually a second filter returning 403 on mismatch.
5. **Why name the `Config` field `enabled`, not `isEnabled`?** Lombok's `@Data` generates `isEnabled()` for the `enabled` field; naming the field `isEnabled` breaks Spring's property binding from YAML `args`.
6. **Is reading `X-User-Id` safe on its own?** Only if downstream services are unreachable except through the gateway and the gateway strips any inbound `X-User-Id`. Otherwise a caller could spoof identity, and each service must validate the token itself.
