Each microservice has its own `application.yml`, so changing a config value means editing the file in every service and restarting it. With 10+ services this is slow and error-prone. A Centralized Configuration Server moves all config into one Git repo, so a single edit propagates everywhere.

```
Without Config Server:
  Order Service     → application.yml (local)
  Inventory Service → application.yml (local)
  API Gateway       → application.yml (local)
  Change DB URL? → edit each file → restart each service

With Config Server:
  All services → pull config from → Config Server → pulls from → GitHub
  Change DB URL? → edit one file in GitHub
```

---

## How It Works

A Spring Cloud Config Server is a dedicated service that acts as a centralized repository, so all microservices retrieve their configuration dynamically at runtime. It manages different environments (`dev`, `test`, `prod`) via Spring profiles, so each environment has its own DB URLs, API keys, and so on.

```
┌──────────────────┐        ┌───────────────────────┐        ┌─────────────┐
│  Order Service   │        │  Spring Cloud         │        │   GitHub    │
│  (Config Client) │◄───────│  Config Server        │◄───────│   Repo      │
├──────────────────┤        │  port: 8888           │        │             │
│  Inventory Svc   │◄───────│                       │        │ application │
│  (Config Client) │        │  Pulls configs from   │        │ .yml        │
├──────────────────┤        │  GitHub on startup    │        │ order-svc   │
│  API Gateway     │◄───────│                       │        │ .yml        │
│  (Config Client) │        │                       │        │ inv-svc     │
└──────────────────┘        └───────────────────────┘        │ .yml        │
                                                             └─────────────┘
```

1. Config Server starts and clones the GitHub repo.
2. Microservices start and ask the Config Server for their config (by service name plus profile).
3. Config Server returns the matching properties.
4. Config changes in GitHub are picked up on the next restart.

## Setting Up the Config Server

Create a `config-server` from [start.spring.io](https://start.spring.io/) with dependencies Config Server and Eureka Discovery Client, then enable and configure it.

**Enable the server**:

```java
@SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(ConfigServerApplication.class, args);
    }
}
```

**Configure `application.yml`**:

```yaml
spring:
  application:
    name: config-server
  cloud:
    config:
      server:
        git:
          uri: https://github.com/your-username/ecommerce-config-repo
          username: your-github-username
          password: your-github-personal-access-token
          default-label: master                         # or main
          clone-on-start: true

server:
  port: 8888

eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka
```

**Verify it**: hit the config endpoints, which return the resolved config per service and profile.

```
GET http://localhost:8888/order-service/default
GET http://localhost:8888/order-service/dev
GET http://localhost:8888/inventory-service/default
```

> **Note**: for a private repo, create a GitHub fine-grained Personal Access Token (`Settings → Developer Settings → Personal Access Tokens`) with Contents: Read on the config repo. Copy it immediately; it is shown only once.

## Setting Up Config Clients

Add the following to every microservice that should pull config from the server. The local `application.yml` only needs the service name and the config server location; everything else comes from the GitHub repo.

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-config</artifactId>
</dependency>
```

```yaml
spring:
  application:
    name: order-service
  config:
    import: configserver:http://localhost:8888
```

## Shared and Profile-Specific Config

Properties common to all services go in the root `application.yml` in the repo; a service can override any of them in its own file. Profile-specific files override the service default.

```yaml
# application.yml in the repo: inherited by ALL services
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka
```

```yaml
# order-service.yml (default)
my:
  variable: order-github-default
```

```yaml
# order-service-dev.yml (dev): overrides the default value
my:
  variable: order-github-dev
```

Read it with `@Value`, and activate a profile via `spring.profiles.active` (or a JVM flag / env var):

```java
@Value("${my.variable}")
private String myVariable;
```

```yaml
spring:
  profiles:
    active: dev
```

## Securing the Config Server

The config server hands out every service's secrets (DB passwords, API keys); anyone who can reach it can read them. In production:

- Put it on an internal network only, not exposed via the API gateway.
- Add HTTP Basic auth on the server (`spring.security.user.name` / `password`) and have clients send credentials via `spring.cloud.config.username` / `password`.
- Store sensitive values encrypted in the Git repo using `{cipher}` placeholders; the server decrypts on read with a configured key.
- Restrict the GitHub PAT to read-only on the single config repo.
- Use a dedicated branch per environment (`dev`, `prod`) for stricter PR-gated promotion instead of a single `master`.

## Q&A

1. **What problem does Spring Cloud Config Server solve?** It centralizes configuration for all microservices in one Git repo, so a single edit propagates everywhere with no per-service `application.yml` edits and redeploys.
2. **How does a microservice locate its config?** By matching `spring.application.name` (and the active profile) to file names in the repo. The client points at the server via `spring.config.import=configserver:http://...`.
3. **What is the role of `application.yml` in the config repo?** It holds global properties inherited by every service (such as the shared Eureka URL). Service-specific files override it.
4. **What is the profile precedence?** Global `application.yml`, then `<service>.yml` (default), then `<service>-<profile>.yml` (active profile overrides defaults).
5. **What is the startup order with Eureka, Config Server, and microservices?** Eureka first, Config Server second (registers with Eureka, clones the repo), then microservices (fetch config and register).
6. **What is the limitation of Config Server alone?** Services do not see config changes until restart. `@RefreshScope` plus Actuator's `/actuator/refresh` solves this (see [13.4 Refresh Configuration without Restart](<13.4. Refresh Configuration without Restart.md>)).
