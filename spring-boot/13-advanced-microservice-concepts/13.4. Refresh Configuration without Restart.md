When a config value changes in GitHub, running microservices still hold the old value in their application context and must restart to pick up the new one. That restart means downtime, which is unacceptable in production. `@RefreshScope` plus Actuator solves it by reloading config at runtime.

> **Reference**: builds on [13.3 Centralized Configuration Server](<13.3. Centralized Configuration Server.md>).

---

## @RefreshScope

A Spring Cloud annotation that enables dynamic refreshing of Spring-managed beans, so their configuration updates at runtime without restarting the application.

- Only beans explicitly marked with `@RefreshScope` are refreshed.
- Works together with Spring Cloud Config.
- Requires Spring Boot Actuator to expose the `/actuator/refresh` endpoint.

> **Note**: the Config Server does not auto-detect GitHub changes. It does a fresh `git pull` only when a client requests config, triggered by `/actuator/refresh`.

---

## How It Works

```
1. Config value changes in GitHub
         │
         ▼
2. Call POST /actuator/refresh on the microservice
         │
         ▼
3. Microservice asks the Config Server for the latest config
         │
         ▼
4. Config Server does a fresh git pull from GitHub
         │
         ▼
5. Returns the latest values to the microservice
         │
         ▼
6. Spring recreates @RefreshScope bean instances with the new
   config values (via an AOP proxy)
         │
         ▼
7. The next request gets the new value, with no restart
```

Spring creates an AOP proxy for every `@RefreshScope` bean. Only these beans are reloaded; the rest of the context is untouched, so there is no downtime.

---

## Setup

Add Actuator to every microservice that needs refresh support, expose the endpoint, annotate the relevant beans, and trigger the refresh after each change.

**Add the Actuator dependency**:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

**Expose the refresh endpoint** (in the global `application.yml` in the config repo):

```yaml
management:
  endpoints:
    web:
      exposure:
        include: refresh,health,info    # production: expose only what you need
```

**Annotate refreshable beans** with `@RefreshScope`:

```java
@RestController
@RefreshScope                           // marks this bean as refreshable
public class OrderController {

    @Value("${my.variable}")
    private String myVariable;

    @GetMapping("/hello")
    public String hello() {
        return "my.variable = " + myVariable;
    }
}
```

**Trigger the refresh** after changing a value in GitHub. This is a POST with no body; the response lists the beans that were refreshed.

```
POST http://localhost:8081/actuator/refresh
```

## Feature Flags Use Case

A practical use is toggling features on or off at runtime without restarting. Mark the config bean `@RefreshScope`, read the flag where needed, and flip the value in GitHub followed by `POST /actuator/refresh`.

```java
@Configuration
@RefreshScope
public class FeaturesEnabledConfig {

    @Value("${features.user-tracking.enabled}")
    private boolean userTrackingEnabled;

    public boolean isUserTrackingEnabled() {
        return userTrackingEnabled;
    }
}
```

```java
@RestController
@RequiredArgsConstructor
public class OrderController {

    private final FeaturesEnabledConfig featuresEnabledConfig;

    @GetMapping("/hello")
    public String hello() {
        return featuresEnabledConfig.isUserTrackingEnabled()
            ? "User tracking enabled"
            : "User tracking disabled";
    }
}
```

```properties
# order-service-dev.properties in the config repo
features.user-tracking.enabled=true
```

## Don't Abuse @RefreshScope

- Do not put `@RefreshScope` on every bean. Each refresh re-initializes all marked beans, which is unnecessary overhead.
- Use it only on beans whose config must change dynamically.

Good candidates are values that change occasionally and should not trigger a redeploy:

| Use Case             | Example                              |
| -------------------- | ------------------------------------ |
| Feature flags        | `features.user-tracking.enabled`     |
| Dynamic DB config    | Connection pool size, timeout        |
| API rate limits      | `api.rate-limit.requests-per-second` |
| External service URLs | Third-party API endpoints           |

> **Note**: values injected into non-`@RefreshScope` singletons stay at their startup value. `DataSource`, connection pools, Kafka producers/consumers, server `port`, JPA/Hibernate config, and `@ConfigurationProperties` beans not annotated with `@RefreshScope` need a restart (or explicit re-binding) to change.

> **Note**: `/actuator/refresh` mutates application state, so never expose it publicly. Bind it to an internal management port (`management.server.port`) or protect it with Spring Security. For fan-out across many instances, pair it with Spring Cloud Bus plus a broker (RabbitMQ/Kafka) so one `/busrefresh` call refreshes all replicas.

## Q&A

1. **What does `@RefreshScope` do?** Marks a bean for runtime reloading. Spring wraps it in an AOP proxy; on `/actuator/refresh`, the underlying instance is recreated with the latest config, without restarting the app.
2. **Why isn't `@RefreshScope` on by default for every bean?** Reloading every bean would be expensive and risky (tearing down singletons, reconnecting pools). Spring refreshes only beans you explicitly opt in.
3. **What endpoint triggers a refresh, and what HTTP method?** `POST /actuator/refresh` with no body. The response lists which beans were refreshed.
4. **Does the Config Server auto-detect Git changes?** No. It does a fresh `git pull` only when a client requests config (typically triggered by `/actuator/refresh`). For push-based fan-out, add Spring Cloud Bus plus a message broker.
5. **What dependency is required besides Spring Cloud Config?** `spring-boot-starter-actuator`; without it the `/refresh` endpoint does not exist.
6. **What will not refresh even with the endpoint exposed?** Values in non-`@RefreshScope` singletons, plus infrastructure like `DataSource`, connection pools, server `port`, and most auto-configured beans. Those still need a restart.
