In a microservice system a single request flows through multiple services, so when something is slow or broken you would otherwise grep each service's logs separately, which is impractical past a handful of services. Distributed tracing visualizes the whole flow, shows how long each service took, and pinpoints bottlenecks.

```
User Request → API Gateway → Order Service → Inventory Service
                                           → Payment Service
```

---

## Key Concepts

- **Trace**: one complete request journey from start to finish across all services, identified by a unique Trace ID shared by every service involved.
- **Span**: a single unit of work within a trace (one service call). Each span has its own Span ID but carries the parent's Trace ID.

```
Trace (one request, one Trace ID)
  │
  ├── Span A  → API Gateway          (800ms)
  │     │
  │     ├── Span B  → Order Service  (709ms)
  │     │     │
  │     │     ├── Span C → Inventory Service  (some ms)
  │     │     └── Span D → Payment Service    (some ms)
  │     │
  │     └── Span E  → another call   (some ms)
```

The same Trace ID flows through every span; each new request gets a fresh Trace ID.

---

## Tools

- **Micrometer**: a vendor-neutral metrics façade that instruments your Spring Boot app, recording start time, end time, Trace ID, and Span ID for every request. It can feed multiple backends (Zipkin for tracing, Prometheus for metrics, Elastic for dashboards) and replaces the older Spring Cloud Sleuth.
- **Zipkin**: a dedicated tracing UI that receives data from Micrometer and visualizes the full request tree, time per service, and dependency graph. Runs standalone on port `9411` ([install guide](https://zipkin.io/pages/quickstart)).

> **Note**: alternatives to Zipkin are Jaeger (CNCF, native OpenTelemetry support) and Grafana Tempo (cheap object-storage backend, correlates with Loki and Prometheus). Micrometer Tracing supports any of them; swap the bridge dependency (`micrometer-tracing-bridge-otel` for OpenTelemetry exporters).

> **Note**: Brave defaults to the B3 headers (`X-B3-TraceId`, `X-B3-SpanId`); the OpenTelemetry bridge defaults to W3C `traceparent` (the modern interop standard). Pick one consistently across all services, or configure both. Mixed propagation breaks the trace.

## Setup

Run a Zipkin server, add the tracing dependencies to each microservice, configure sampling, and register the observation bean.

**Run Zipkin** (dashboard at `http://localhost:9411`):

```bash
java -jar zipkin-server.jar
# or
docker run -d -p 9411:9411 openzipkin/zipkin
```

**Add dependencies to each microservice**:

```xml
<!-- Micrometer observation -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-observation</artifactId>
</dependency>

<!-- Tracing bridge (Brave): sends data to Zipkin -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>

<!-- Zipkin reporter -->
<dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
</dependency>

<!-- OpenFeign + Micrometer: traces Feign calls -->
<dependency>
    <groupId>io.github.openfeign</groupId>
    <artifactId>feign-micrometer</artifactId>
</dependency>

<!-- Actuator (if not already present) -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

**Configure sampling and the Zipkin URL** (in the global `application.yml` in the config repo). The default sampling probability is `0.1` (10%); keep it low in production to save resources.

```yaml
management:
  tracing:
    sampling:
      probability: 1.0      # trace 100% of requests (dev only, use ~0.1 in prod)

spring:
  zipkin:
    base-url: http://localhost:9411
```

**Register an observation customizer** to skip noisy actuator/heartbeat traces:

```java
@Configuration
public class AppConfig {

    @Bean
    ObservationRegistryCustomizer<ObservationRegistry> skipActuatorEndpoints() {
        return registry -> registry.observationConfig()
            .observationPredicate((name, context) -> {
                if (context instanceof ServerRequestObservationContext ctx) {
                    return !ctx.getCarrier().getRequestURI().startsWith("/actuator");
                }
                return true;
            });
    }
}
```

## How It Works at Runtime

```
API call made
      │
      ▼
Micrometer assigns a Trace ID + Span ID to the request
      │
      ▼
The Trace ID is passed to every downstream service call
      │
      ▼
Each service records its own Span (start time, end time, Span ID)
      │
      ▼
All spans are reported to the Zipkin server (port 9411)
      │
      ▼
Zipkin UI shows the full trace tree with timings
```

---

## Zipkin Dashboard

**Traces view**: lists all recorded traces, one row per request. Clicking a trace expands the full span tree, and clicking a span shows its individual timing and metadata.

```
API Gateway        [800ms] ──────────────────────────────
  Order Service    [709ms] ─────────────────────────
    Inventory Svc  [some ms] ──────────
```

**Dependencies view**: a graph of how services call each other (`API Gateway → Order Service → Inventory Service`). With hundreds of services this becomes complex; filter by service name to focus on one and its connections.

**Filtering and sorting**:

- Filter by service name, time range, or duration; sort by start time or duration to find the slowest requests.
- Eureka heartbeats appear as traces every 30s and can be ignored (the observation predicate above filters them out).

## Tracing vs Logging

|         | Distributed Tracing (Zipkin)         | Distributed Logging (ELK)        |
| ------- | ------------------------------------ | -------------------------------- |
| Purpose | Track request flow and timing         | Centralized log storage and search |
| Shows   | Which services ran and for how long   | What happened inside each service  |
| Tool    | Zipkin plus Micrometer               | ELK Stack                        |

> **Reference**: [13.6 Centralized Logging with ELK Stack](<13.6. Centralized Logging with ELK Stack.md>) covers viewing all microservice logs in one place.

## Q&A

1. **What is distributed tracing and why do you need it?** It tracks a single request across multiple services using a shared Trace ID, so you can visualize the call graph and timings instead of grepping each service's logs.
2. **Trace vs Span?** A Trace is the whole request journey (one Trace ID). A Span is one unit of work within it (one service call), with its own Span ID but the same Trace ID.
3. **What replaced Spring Cloud Sleuth?** Micrometer (specifically `micrometer-tracing` with the Brave bridge for Zipkin). Sleuth is not maintained for current Spring Boot versions.
4. **What does sampling probability control?** The fraction of requests Micrometer records. `1.0` traces everything (dev); `0.1` (10%) is typical for production to limit overhead and storage.
5. **How does the Trace ID propagate downstream?** Micrometer adds it to outgoing HTTP headers (`b3` or `traceparent`). With `feign-micrometer`, OpenFeign clients carry it automatically; MVC/WebFlux instrumentation does the same for incoming calls.
6. **Tracing vs centralized logging, when do you reach for each?** Tracing (Zipkin) shows where time is spent; logging (ELK) shows what happened inside each service. They share the Trace ID, so you pivot between them when debugging.
