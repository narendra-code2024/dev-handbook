Zipkin handles distributed tracing (timing and request paths) but not deep log analysis. When something breaks you would otherwise check each service's logs individually, which is tedious past a handful of services. The ELK Stack centralizes all microservice logs into one searchable place, offering powerful search (such as by Trace ID across all services), long-term storage, and dashboards with alerting.

---

## Alternatives to ELK

- **Grafana Loki plus Promtail and Grafana**: Loki indexes only labels, not full text, so storage cost is dramatically lower; a good fit if you already run Prometheus/Grafana for metrics and Tempo for traces.
- **OpenSearch plus OpenSearch Dashboards**: AWS-led fork of Elasticsearch/Kibana under Apache 2.0; a drop-in replacement after Elastic moved to SSPL.
- **Filebeat instead of Logstash**: a lighter agent that ships logs to Elasticsearch directly when you do not need Logstash's transformation pipeline.
- **Cloud-managed**: AWS CloudWatch Logs plus Insights, GCP Cloud Logging, or Datadog Logs; less operational overhead at the cost of vendor lock-in.

The setup below applies to OpenSearch with minor URL and dashboard differences.

---

## What is the ELK Stack?

Three open-source tools from Elastic, used together:

```
Spring Boot Apps → logs → Logstash → Elasticsearch ← Kibana (visualize)
```

- **Elasticsearch**: a NoSQL store (built on Lucene) that indexes log data and excels at fast aggregation queries. An Elasticsearch index is roughly equivalent to a SQL table.
- **Logstash**: a pipeline that collects, parses, transforms, and ships log data into Elasticsearch. Configured via a `.conf` file with an input (log files) and an output (Elasticsearch).
- **Kibana**: the analytics and visualization layer on top of Elasticsearch, used to search, filter, and build dashboards without writing raw queries.

---

## How It All Works Together

```
Spring Boot Microservices
  │  generate log files (via logback)
  ▼
Logstash (reads log files via logstash.conf)
  │  parses each line as a structured event
  │  ships events in near real-time
  ▼
Elasticsearch (indexes the log events)
  │  logs are now searchable by Trace ID, service name, timestamp, etc.
  ▼
Kibana Dashboard
  │  visualize, search, filter, alert
```

### Run Elasticsearch

```bash
cd elasticsearch-<version>
bin/elasticsearch
```

It runs on `https://localhost:9200` (note https, since `elasticsearch.yml` enables SSL by default via `xpack.security.enabled: true`). On first run it prints the `elastic` username, a one-time password, an enrollment token for Kibana, and the CA certificate fingerprint. Copy the password immediately.

> **Note**: to reset the password later, run `bin/elasticsearch-reset-password -u elastic`.

### Run Kibana

```bash
cd kibana-<version>
bin/kibana
```

On first run Kibana prints a setup URL. Open it, paste the enrollment token from Elasticsearch, then log in as `elastic`. The dashboard is at `http://localhost:5601`.

### Configure Logback in Each Microservice

Create `logback-spring.xml` in `src/main/resources` of each microservice. The pattern includes the Trace ID and Span ID from Micrometer, which is what enables cross-service search by Trace ID in Kibana, and each service writes to its own log folder.

```xml
<configuration>
  <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{yyyy-MM-dd HH:mm:ss} [%thread] [%X{traceId},%X{spanId}] %-5level %logger{36} - %msg%n</pattern>
    </encoder>
  </appender>

  <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>logs/${spring.application.name}/application.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
      <!-- New file per day, max 10MB per file -->
      <fileNamePattern>logs/${spring.application.name}/application-%d{yyyy-MM-dd}.%i.log</fileNamePattern>
      <timeBasedFileNamingAndTriggeringPolicy
        class="ch.qos.logback.core.rolling.SizeAndTimeBasedFNATP">
        <maxFileSize>10MB</maxFileSize>
      </timeBasedFileNamingAndTriggeringPolicy>
    </rollingPolicy>
    <encoder>
      <pattern><!-- same pattern as STDOUT above --></pattern>
    </encoder>
  </appender>

  <root level="INFO">
    <appender-ref ref="STDOUT"/>
    <appender-ref ref="FILE"/>
  </root>
</configuration>
```

> **Note**: prefer structured JSON logs in production. Plain-text patterns force Logstash to grok-parse every line (fragile and CPU-heavy). With `logstash-logback-encoder`'s `LogstashEncoder`, Logback writes one JSON object per event with `timestamp`, `level`, `message`, `traceId`, `spanId`, `service`, MDC fields, and split stack traces already as fields, so Logstash just forwards and Kibana filters become trivial (`level: ERROR AND service: order-service`).

### Configure Logstash

Create `logstash.conf` inside the Logstash folder, pointing its input at your project's logs directory and its output at Elasticsearch.

```ruby
input {
  file {
    type  => "log"
    # Absolute path to your project's root logs folder
    # e.g. /Users/john/documents/ecommerce/logs/**/*.log
    path  => "<your-project-root>/logs/**/*.log"
    start_position => "beginning"
  }
}

output {
  elasticsearch {
    hosts    => ["https://localhost:9200"]
    index    => "spring-boot-logs-%{+YYYY.MM.dd}"
    ssl_certificate_verification => false
    user     => "elastic"
    password => "<your-elasticsearch-password>"
  }
}
```

### Run Logstash

```bash
cd logstash-<version>
bin/logstash -f logstash.conf
```

Logstash reads all log files, converts each line into a structured event, and ships them to Elasticsearch.

### Create a Data View in Kibana

In Kibana go to Analytics, Discover, Create Data View; set the index pattern to `spring-boot-logs-*` and the timestamp field to `@timestamp`, then save. Logs are now visible and searchable.

```
[inventory-service] Reducing stock for product      traceId=abc123
```

## Tracing vs Logging Summary

|            | Zipkin (tracing)                   | ELK Stack (logging)                   |
| ---------- | ---------------------------------- | ------------------------------------- |
| Purpose    | Request flow and timing             | Centralized log storage and search    |
| Shows      | Which services ran and for how long | What happened inside each service      |
| Search by  | Trace ID (visual timeline)         | Trace ID, service name, log level, time |
| Best for   | Finding bottlenecks                | Debugging errors and exceptions        |

## Q&A

1. **What does each piece of ELK do?** Elasticsearch stores and indexes log events; Logstash ingests, parses, and ships logs from files into Elasticsearch; Kibana is the UI for search, dashboards, and alerts.
2. **How do logs from a Spring Boot app reach Elasticsearch?** Logback writes structured log lines (with Trace ID and Span ID) to rolling files. Logstash tails those files via its `input { file ... }` config and ships each event to Elasticsearch.
3. **Why include Trace ID and Span ID in the log pattern?** It links logs to Zipkin traces and lets you pivot from a slow trace into the actual log lines from every service for that request.
4. **What is an Elasticsearch index?** Roughly a SQL table: a named collection of documents (log events). The Logstash `index` setting routes events into a specific one (e.g., `spring-boot-logs-2026.04.25`).
5. **Why use ELK if you already have Zipkin?** Zipkin shows where time is spent across services; ELK shows what the application logged (errors, stack traces, business events). Together they give complete visibility, joined by the Trace ID.
6. **Why `logback-spring.xml` over plain `logback.xml`?** Spring Boot loads `logback-spring.xml` after the environment is initialized, so you can use Spring properties like `${spring.application.name}` in patterns and file paths.
